# Phase 5 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.
>
> Upstream: D-01..D-28 in `05-CONTEXT.md` are locked and are not re-opened. Spacing scale, the four typography roles, the neutral palette, the accent-reserved list, the notice and skip-tag chrome, the selector pattern, the chart-geometry conventions and the copy conventions are inherited from `02-UI-SPEC.md`, `03-UI-SPEC.md` and `04-UI-SPEC.md`. Everything this phase adds beyond them is listed under "Deltas from Phase 4" so the checker can audit it in one place. Where CONTEXT left a choice to Claude's discretion, the decision is made here with a one-line rationale (marked **Decision**).
>
> Scope: the `Player_statistics` section body (vehicle table), a **new** sixth `Financial_data` section (premium-time chart, virtual-currency charts), and the `Payment_history` section body (real-money spend summary). Login history and the world map are Phase 6; phone-width and touch polish is Phase 7 (section 14 lists what this phase must not preclude and what must not break at 375px).
>
> Evidence base for column names: the header lines of the real 2021 sample export (`~/Downloads/export/1234567_2021-10-12.zip`, local only). No row data was read or is quoted. Parsing is by header name and tolerant of missing columns (CONTEXT, Defensive parsing).

## Spacing Scale

Declared values (multiples of 4) — the Phase 2/3/4 scale, unchanged:

| Token | Value | Usage in this phase |
|-------|-------|---------------------|
| xs | 4px | Label-to-control gap in a selector; `dt`/`dd` gap; gap between tooltip lines; gap between legend items; padding-y of a note line; gap inside a spend card's figure rows |
| sm | 8px | Gap between a chart title, its summary sentence and its graphic; table cell padding-x; tag padding-x; the `h3` bottom padding; gap inside a `<details>` between its summary and content |
| md | 16px | Spend-card padding and gap between spend cards; gap between the controls in the control row; gap between a chart block's parts; `dl` column gap |
| lg | 24px | Vertical gap between the sub-blocks of every new block (controls, header, summary, table; premium and currency blocks; spend intro and cards) |
| xl | 32px | not used as spacing |
| 2xl | 48px | not used |
| 3xl | 64px | not used |

Every new block is one flex column with `gap: 24px` inside the section card (whose own `gap: 8px` and `padding: 16px` are unchanged). Every flex/grid child that can hold untrusted text (vehicle IDs, currency codes, game codes, unrecognised premium strings, battle-type codes) sets `min-width: 0` and `overflow-wrap: anywhere`; in the windowed table that rule becomes single-line ellipsis with the full text in `title` (see section 3).

**Exceptions (pre-existing, continued):** `12px` (select padding-x), stroke widths 1px / 2px / 3px, `--nav-offset: 72px`, and every Phase 4 chart-geometry exception (still owned by Phase 4's charts, none reused here).

**New exceptions — table and chart mark geometry, not layout spacing.** Declared once here so the checker can audit them; nothing else in the phase may use an off-scale value.

| Item | Value | Derivation |
|------|-------|------------|
| Vehicle table row height (body and header) | 40px, fixed | Windowing needs a constant row height; 40 = 19.6px line + 20px vertical breathing room, a multiple of 4 |
| Vehicle table viewport (`vehicle-scroller`) | `max-height: 480px` (header + 11 rows) | Shows a meaningful page of rows without pushing the rest of the section below the fold |
| Window overscan | 6 rows above and below the viewport | Keeps scrolling smooth; DOM holds at most about 30 body rows plus 2 spacer rows |
| Column widths (classes, no inline style) | vehicle 160px, battles 88px, win rate 96px, average damage 112px, frags 80px, total XP 96px; extras 96px (numeric), 160px (date) | Six default columns sum to 632px, which fits the 638px card content width at 720px. Widths are header-text width at 14px/600 plus 16px padding plus the 16px sort arrow, rounded up to a multiple of 4 |
| Warships all-battles view: win rate and average damage columns | 176px each | Fits the locked cell text "Available per battle type" |
| Chart y-axis gutter | 56px | Fits `−27M` at 14px with 4px of padding (the compact maximum of the 1,572-month axis, which the formatter renders as `27M`) |
| Chart bar pitch | 16 / 12 / 8 / 4px, chosen per chart (see section 6) | Largest pitch for which `months × pitch ≤ 576px`; 576 + 56 = 632px fits 638px |
| Chart bar width | pitch − 1px (15 / 11 / 7 / 3px), 1px gap | Off-scale by construction; bars are marks, not layout |
| Chart plot height | premium 96px; currency 80px above the zero line and 80px below | Both multiples of 4; the diverging chart is symmetric so deposits and withdrawals share one scale |
| Chart top padding / x-axis band | 8px / 24px | One 14px line at 1.4 in the band |
| Chart SVG size | premium `56 + plotWidth + 4` × 128; currency `56 + plotWidth + 4` × 192 | Fixed size, never scaled, so axis text stays 14px |
| Tag (nation tag) | 14px text, padding `0 8px`, 1px border, radius 6px | Same radius as tiles and notices |
| Focus ring column on a month | full plot height, width `max(pitch, 8px)`, 3px accent stroke outside a 1px `#ffffff` inner stroke | Same two-tone ring as Phase 4's heatmap cell, so it stays visible on a 3px bar |

**Scale rule for the bar charts.** Linear, from zero, never min-max and never log. One domain per chart: `[0, M]` where `M` is the largest single-month deposit or withdrawal (diverging) or the largest single-month day count (premium). A month with a non-zero value is drawn at least 2px tall so it stays visible. Bars are never colour-graded by value; the heights carry the magnitude. Each currency has its own domain (D-15), and a Caption says so.

**Deltas from Phase 4 (for the checker):**
1. Two new data colours, `--flow-in` and `--flow-out` (marks only; not text, not chrome, not status).
2. `ChartTooltip` extended with optional extra Caption lines (no new size or weight).
3. `ExcludedNotice` takes its pill and explanation as props (chrome unchanged).
4. Sort arrows are `aria-hidden` text characters (`↑` / `↓`) on the sorted header only; direction is also in `aria-sort` and the sorted header's `#f1f3f4` surface.
5. Table and chart mark geometry exceptions listed under Spacing.
6. Sixth nav link and sixth section (see sections 1 and 2); the nav now overflows its own container at 720px.
7. Page-wide explicit `aria-live` attribute count rises from two to three (one new region, `player-stats-status`; see section 13).
8. Phase 5 number formatting uses the viewer's locale (D-25), where Phase 4's `formatNumber` pins `en-US`; see UI Considerations (unresolved row).
9. **Recorded deviation from D-27.** D-27 says the new charts reuse Phase 4's `ChartLegend`. They do not: `ChartLegend` is the **Less-to-More** ramp legend, with ramp swatch classes and ramp copy, and a flow chart's legend has to name two directions (`Deposited (above the line)` · `Withdrawn (below the line)`) that the ramp scale has no meaning for. The flow legend is therefore a **new component that copies `ChartLegend`'s chrome**, so the two legends look like siblings without sharing a contract. The deviation is deliberate and approved here rather than discovered mid-build.

### 1. Placement, section order and nav (D-01, D-02)

Anchor ids: `activity-history`, `player-statistics`, `financial-data` (new), `payment-history`, `user-info`, `not-yet-supported`. The new section uses the unchanged `DashboardSection` shell and `scroll-margin-top: var(--nav-offset)`. Its title is the folder name exactly as written, `Financial_data`.

Status per section (pure derivation in `dashboard-status.ts`, shared by nav and cards):

| Section | `ready` when | Greyed states (unchanged wording) |
|---------|--------------|-----------------------------------|
| `player-statistics` | at least one parsed row in the folder | `no-export`, `empty`, `not-loaded` |

To keep the current link visible, when `aria-current` moves the nav sets **its own** `scrollLeft` so the current link is fully inside the nav (never `scrollIntoView`, which would scroll the page). Reduced motion: the nav scroll is instant. The 3px underline and the focus ring must not be clipped at either end of the scroll range.

### 2. State matrices

Each new block carries `data-state`.

**`player-stats`** (`data-testid="player-stats"`)

| `data-state` | When | What renders |
|--------------|------|--------------|
| `loading` | Dataset displayed, the table model for the current title not yet received | The `h3`, Body text `Calculating vehicle statistics...` in the status line; no controls, header, summary or table. `aria-busy="true"` on the block |
| `ready` | Model received | Everything in section 1 for the chosen title |
| `updating` | `ready`, and a new title or battle type was requested | The previous table stays on screen unchanged; status line reads `Updating table...`; `aria-busy="true"` on the table region. The latest request wins and a response for an older selection is ignored (the Phase 4 rule, same `superseded`-is-not-an-error handling) |
| `error` | The worker query or aggregation failed | The `h3` and the destructive-chrome message (copy below), `role="alert"` with no `aria-live` attribute. No retry button: dropping the export again is the retry and the dataset on screen is unchanged |

Inside `ready`, `data-title-state` on the block is one of `ready`, `not-in-export` or `no-rows`:

| `data-title-state` | When | What renders |
|--------------------|------|--------------|
| `ready` | The chosen title has vehicle rows | The full layout |
| `not-in-export` | No file of that title exists in the folder | Controls row (the title select stays), then one neutral-info line `{Title} is not in this export`. No header, summary, table, hints |
| `no-rows` | Title files exist but its vehicle file parsed to zero rows | Controls row, the per-title header if its account file has values, then `This export contains no vehicle rows for {Title}`. No summary or table |

**`premium-block` and `currency-block`**: `data-state` is one of `loading`, `ready`, `not-in-export`, `no-rows`, `no-usable`, `error`.

| `data-state` | When | What renders |
|--------------|------|--------------|
| `loading` | Aggregate not yet received | The `h3` and Body `Calculating financial data...` with `role="status"` (no `aria-live` attribute); `aria-busy="true"` |
| `ready` | At least one usable row | Section 1 layout for that sub-block |
| `not-in-export` | The file is absent | `h3` and Body `Not in this export` (D-02, Phase 3 D-10 wording) |
| `no-rows` | The file is present with zero rows | `h3` and Body `This export contains no rows for Premium time` / `...for Virtual currency` |
| `no-usable` | Rows exist but none could be used | `h3`, Body `No premium operations with a recognisable duration were found in this export.` / `No virtual-currency operations with a known type and a numeric amount were found in this export.`, then the excluded pill |
| `error` | Query or aggregation failed | The destructive-chrome message (copy below) |

**`spend-block`**: `loading`, `ready`, `no-usable` (rows exist but none has a recognisable status; Body `No orders with a recognisable status were found in this export.`), `error`.

The `Financial_data` section itself is `ready` if either file has rows (D-02); a sub-block that is absent or empty shows its own state line inside the ready section. Both sub-blocks stay in the DOM in every state, so the section keeps its two `h3`s.

### 3. Vehicle statistics (STATS-01, D-05..D-14)

**Controls row.** `display: flex; flex-wrap: wrap; gap: 16px; align-items: flex-end`. Each control is a column of a Label above the control with a 4px gap (the Phase 4 selector-row). Each `<select>`/`<input>` has `max-width: 100%`, `min-width: 0`.

- **Game (`<select data-testid="player-stats-title-selector">`)**. Label `Game`. Options in fixed order WoT, WoT Blitz, Warships, Warplanes. An absent title keeps its option with the suffix ` (not in this export)`; a title whose vehicle file parsed to zero rows has the suffix ` (no rows in this export)`. Options are never disabled, so the reason is readable in the content area as well as in the option text. Default selection on load is the first title with vehicle rows; if none has rows, WoT. The style is the Phase 4 select exactly (Label 14/600 `#3c4043`, `padding: 8px 12px`, `1px solid #80868b`, radius 6px, bg `#ffffff`, hover bg `#f1f3f4`, accent focus ring).
- **Battle type (`<select data-testid="player-stats-battle-type-selector">`)**. Label `Battle type`. First option `All battles` (default). Then one option `Battle type {code}` per code present in that title's `*_by_Type` file, ordered by the code's numeric value ascending (plain code-unit order if a code is not an integer); never named. **Decision**, rationale: codes are identifiers, so a stable numeric order is easier to scan than a data-dependent one. When the title has no codes (Warplanes, or no `by_Type` rows) the control is **not rendered** (the same silence as Phase 4's absent split), and neither is the battle-type summary.
- **Search (`<input type="search" data-testid="vehicle-search">`)**. Label `Search vehicles`, no placeholder. Case-insensitive substring match over the cleaned vehicle ID (the part after the nation prefix, D-11). Style as the select but Body 16/400 text. Filtering runs over the already-mapped view rows in memory; the main thread never scans raw `rows` (Phase 2 and 4 rule).
- The selection state (title, battle type, search text, sort, extra columns) is component state, never persisted (D-28). Resetting rules: switching **title** resets the battle type to All, the sort to battles descending, the search to empty and the extra columns to none; switching **battle type** resets the sort and the search but keeps the extra columns (**Decision**, rationale: the same fields mostly exist in both views, so dropping the user's chosen columns on every battle-type change would be churn). A dataset replace or Clear resets everything (D-28), and an index or code absent from the new dataset is never displayed.

**Per-title header (D-13).** A `<dl data-testid="player-stats-header">`, `display: grid; grid-template-columns: max-content 1fr; gap: 4px 16px`. Two rows: `Lifetime battles` → the account file's battle count, exact grouped number; `Premium expires` → the account file's premium-expiry cell **as written** (`PREMIUM_EXPIRES_AT` for WoT, `PREMIUM_EXPIRY_TIME` for the others), no date parsing, no timezone claim, so a value like `1970-01-01 00:00:00` is shown as written. A missing column shows `not in export`; `N/A` shows `not available`; `N/D` shows `not defined`. ### 4. Premium-time timeline (FINANCE-01, D-19, D-20)

- **Source.** `Operations_with_Premium_Days.csv` (`PREMIUM`, `CURR_PREMIUM`, `CREATED`, `UPDATED`). One bar per month from the first to the last premium operation's month with a usable row, every month in between drawn (a month with nothing is an empty column), so a gap in the history is visible. **Amended after UAT G-05-3:** the date column is `CURR_PREMIUM`, which the real export writes the operation datetime into (per the UAT G-05-3 real-export comparison); `CREATED` is used only for a file in which no row's `CURR_PREMIUM` reads as a date.
- **Value.** Premium days granted in that month (D-19): `N day(s)` → N, `... N sec` → N ÷ 86400. A **withdrawal** row — the word `withdrawal`, either as one word or the two-word form the export uses, or a count and `sec` with no positive day amount — is a removal of time, not a grant: it is never charted. Premium days granted are summed in integer seconds and converted to days only for display, so no rounding enters the sum. Rows are bucketed by the year and month parts of the date column chosen by the rule in **Source** — `CURR_PREMIUM` where it holds a readable date, `CREATED` otherwise — **as written**, no timezone conversion (Phase 4 D-01). **Amended after UAT G-05-3:** the column was `CREATED` alone, which in a real export is a bulk-migration stamp equal to `UPDATED` and shared by many rows, so a whole history collapsed onto one meaningless month.
- **A readable date.** A date is readable when it parses — ISO or dotted day-first — **and** its year is from 1970 to 2100 inclusive. This is the same window section 5 uses, and it bounds the month axis at **1,572 months**: any later plan sizing the axis or the scroller computes from that number rather than from an unbounded span.
- **Chart.** Single-direction bars, `--flow-in`, domain `[0, M]` with `M` the largest month. Geometry per section 6. The y-axis shows `0` at the baseline and the compact maximum at the top (`title` carries the exact value). A Caption under the `h4` says `Dates are as recorded in the export.`
- **Summary sentence (D-14).** Body, under the `h4`: `Premium time was granted in {m} of {t} months: {d} in total across {n} operations. The largest month was {YYYY-MM} with {d2}.` Day amounts use the rule: whole numbers as integers, otherwise one decimal; the unit is `day` when the rendered numeral is exactly `1`, otherwise `days` (the Phase 4 `formatHours` unit rule applied to days).
- **Tooltip** (shared element; hover and keyboard focus): line 1 `{YYYY-MM}`; line 2 `{d} granted · {n} grants`; extra lines: the grant sizes in that month, most frequent first, at most three then `+{k} more sizes` (`{size} × {count}, ...`), then `Dates as recorded in the export`. An empty month reads line 2 `No premium granted` and only the final extra line.
- **Excluded rows (D-20).** Rows whose premium value is not a recognisable duration or is a withdrawal, or whose date cannot be read, are not counted in the chart. Every one of them is counted in the amber pill `{n} premium row(s) excluded` with the Caption explanation, and the distinct strings of rows excluded for an unrecognised value or because they are withdrawals are listed in a `<details data-testid="premium-unrecognised">` (`Premium values not charted ({k})`): a `<ul>` of the strings as written (plain text, wrapped, at most 20 then `and {k} more`). A row excluded **only** for an unreadable date is counted in the pill and not listed, because its premium string is fine and listing it would imply the value was the problem. A blank value is counted and not listed. The heading names what the list now holds rather than what it used to; the previous wording is recorded in Amendments (plan 05-08). The test id `premium-unrecognised` is unchanged, so nothing downstream has to re-derive it. The pill is never rendered at zero.
- **Monthly data table (D-14).** A `<details>` under the chart (`Monthly data table`), closed by default. Its `<table>` (`Month`, `Days granted`, `Grants`) renders its rows **only while the disclosure is open** (so a closed disclosure adds no row nodes), inside a `max-height: 320px` scroller, exact grouped values, one row per drawn month, newest first.

### 6. Monthly bar chart component (D-17, D-27)

One hand-rolled SVG component serves both timelines. Its node count scales with months, never with rows.

- **Months.** `months` is the count of calendar months from the first to the last usable month inclusive. Empty months are drawn (empty column). A stray very early or very late year in the data lengthens the axis honestly; it is not collapsed (unlike the Phase 4 calendar) because a bar chart has no row of empty year blocks to fold. If `months > 144` the chart keeps pitch 4px and scrolls horizontally inside its own `overflow-x: auto` scroller.
- **Pitch rule. Decision.** Pitch is the largest of 16, 12, 8, 4px for which `months × pitch ≤ 576`; bar width is `pitch − 1`. Rationale: the plot always fills the card width as well as possible without ever scaling the text.
- **Geometry.** SVG width `56 + months × pitch + 4`, height 128 (premium) or 192 (currency). Column `i` has `x = 56 + i × pitch`. Premium: baseline at `y = 8 + 96`, bars grow up. Currency: zero line at `y = 8 + 80`, deposits grow up, withdrawals grow down. A 1px `#5f6368` zero line spans the plot; 1px `#dadce0` hairlines mark the domain bounds. No other gridlines.
- **X axis (D-26).** Labels are ISO-style `YYYY-MM`, Caption `#5f6368`, set in the 24px band under the plot. The first month is labelled, then every 12 months (every 24 when the pitch is 4px) so labels keep at least 96px apart; a label whose text would run past the right edge of the SVG is skipped. Each label has a 4px tick above it.
- **Nodes per month.** One full-height transparent hit rectangle (`data-testid` cell, role `gridcell`, carries the data attributes and the accessible name), plus at most two bar rectangles. Target: at most `3 × months + 40` SVG nodes per chart, asserted in tests.
- **Interaction.** One delegated `pointerover` listener per chart, never one per node. The tooltip opens on pointer hover over a month's hit rectangle and on keyboard focus of a month, follows the latest of the two, and closes on pointer leave, blur, Escape, and when its anchor has moved (the existing `ChartTooltip` stale-anchor rule). The ring (section Color) is drawn on the hovered or focused month.
- **Accessible structure.** The `<svg>` has `role="grid"`, `aria-label="{chart title}"` and `aria-describedby` pointing at the keyboard hint; one `role="row"` group; one `role="gridcell"` per month with an `aria-label`: premium `{YYYY-MM}: {d} granted, {n} grants` or `{YYYY-MM}: no premium granted`; currency `{YYYY-MM}: deposited {x}, withdrawn {y}, {n} operations` or `{YYYY-MM}: no operations`. Legend swatches and bars are `aria-hidden`; axis labels are readable text.
- **Keyboard (roving focus, one tab stop per chart).**

| Key | Behaviour |
|-----|-----------|
| Tab | Enters the chart on one month (the last month at first, then the last-focused month) and leaves on the next Tab; months are never individual tab stops |
| Left / Right | Previous / next month; stops at the first and last drawn month |
| Home / End | First / last month |
| Escape | Hides the tooltip without moving focus |

  A Caption hint above each chart reads `Use the left and right arrow keys to move between months.` The focused month is scrolled into view horizontally inside the chart's scroller and, vertically, clear of the sticky nav (`scroll-margin-top: calc(var(--nav-offset) + 16px)`).

### 7. Real-money spend summary (FINANCE-03, D-21..D-24)

- **No blended anywhere.** No element on the page, including tooltips, captions, `aria-label`s, `title`s and the document title, contains a sum, an average or a converted figure across currencies. The tooltip never contains an IP, an account name or an order identifier.

**One instance per chart container, not one per page.** `ChartTooltip` is a single-element component reused by every chart that owns one, so this phase ships **two** instances: Phase 4's `PlaytimeCharts` keeps its own (`data-testid="chart-tooltip"`), and the Financial charts share **one** instance hosted by the `Financial_data` card body (`data-testid="finance-tooltip"`), because a premium chart and eight currency charts are one hover context, not nine. The id is supplied through a `testId` prop on `ChartTooltip` whose default stays `chart-tooltip`, so Phase 4's call sites are unchanged. The second instance must not reuse the first id: Phase 4's browser and source-contract tests locate `chart-tooltip` without scoping, and a duplicate id would make those locators ambiguous and break them. Only one pointer exists, so the two instances can never be active at the same time, and every rule above applies to each of them independently.

All new strings and formatters live in `src/lib/ui-copy.ts` with unit tests in `tests/unit/ui-copy.test.ts`; formatters take an optional `locale` argument that defaults to the viewer's locale so tests can pin `'en-US'`.

|-------|------|

### 10. Motion

None. No animation, no transition on bars, cells, rows, sort arrows or the tooltip, and no animated re-layout when a selector changes. Window scrolling uses the browser's native scrolling. The nav's own `scrollLeft` adjustment is instant. Reduced-motion handling for the spinner and smooth anchor scrolling is untouched.

### 11. Accessibility (summary)

- Every state is stated in visible text; colour only reinforces. Chart numbers are available as the summary sentence, the tooltip, the month's accessible name and the monthly data table; table numbers are cell text.
- One new explicit live region: `<p data-testid="player-stats-status" role="status" aria-live="polite" aria-atomic="true">`, present in every state of the Player_statistics block, empty (visually hidden with the clip pattern, not `display: none`) when nothing is happening. It carries `Calculating vehicle statistics...`, `Updating table...` and the selection announcement after a title or battle-type change. The Financial and Payment blocks have no user-initiated change to announce, so their `loading` text and error messages use `role="status"` / `role="alert"` **without** an `aria-live` attribute (the Phase 4 precedent); the page-wide count of explicit `aria-live` attributes therefore becomes three, and `dashboard.spec.ts` updates its assertion from two to three.
- Tab order follows document order. One tab stop per bar chart; the table region is one tab stop plus its sort buttons.
- Table: native semantics, `scope="col"`, `aria-sort`, `aria-rowcount`/`aria-rowindex`; windowed rows still announce their true position.
- Untrusted text (vehicle IDs, currency codes and titles, game codes, battle-type codes, unrecognised premium strings, the search query) is rendered by plain interpolation only: no `{@html}`, wrapped or ellipsised, never placed in a `data-*` attribute that a selector concatenates.

### 12. Data and worker constraints the UI depends on

Not visual, but the contract above assumes them:

- The worker remains the only Dexie owner; the main thread talks to it through typed messages only. Per-title, per-battle-type and per-currency aggregates may be precomputed on import or queried on demand (CONTEXT discretion), but the main thread receives **mapped view rows** (a few thousand compact records for the active title and battle type), never raw `rows`, and sorting and searching run over those.
- `Financial_data` joins the supported categories; a Dexie version bump and any migration follow the Phase 3 D-19 / Phase 4 pattern.
- A stale answer is never displayed: every answer carries the `importedAt` it describes (the Phase 4 pairing), and a request for an older selection is superseded, not rendered.
- A bug in an aggregate must never cost the user their import: a failed aggregate renders the block's `error` state, and the dataset on screen is unchanged.

## Amendments (plan 05-08)

Plan 05-08 is the phase's copy and format settlement: it writes the user's two
open answers into this spec and corrects one example that was wrong on its own
terms. Each change is listed here with its reason, so the approved contract
above and the history of how it reached its current wording stay both readable.
The Color table's values, the spacing scale and every D-number's wording are
unchanged by this appendix.

1. **Premium excluded explanation** (Copywriting Contract, section 4) — now
   "Rows whose premium value is not a recognisable duration or is a withdrawal,
   or whose date cannot be read, are not counted in the chart." *Reason:* the
   user's answer. A withdrawal is a removal of time and was being counted as a
   grant; an unreadable date has no month to fall in. Both were silently
   dropped, so the pill's count disagreed with what the chart did.
2. **Premium disclosure renamed** (Copywriting Contract, section 4) — heading is
   now `Premium values not charted ({k})`, listing the distinct strings of rows
   excluded for an unrecognised value or because they are withdrawals. A row
   excluded only for an unreadable date is counted in the pill and not listed,
   because its premium string is fine; a blank value is counted and not listed.
   The test id `premium-unrecognised` is unchanged. *Reason:* the old heading
   said "unrecognised", which is no longer the only reason a row is absent, and
   a reader who saw a withdrawal listed under it had been told something false.
3. **Section 4 Value bullet** — a withdrawal row is not a grant and is never
   charted; premium days granted are summed in integer seconds and converted to
   days only for display. *Reason:* keeps rounding out of the sum, so the pill
   and the chart cannot disagree because of a per-row fraction.
4. **Currency excluded explanation** (Copywriting Contract, section 5) — now
   "Operations with an unknown type, a non-numeric amount or a date that cannot

   without being counted.
5. **Section 5 Direction bullet** — a negative amount counts as non-numeric.

6. **Readable-date window** stated in sections 4 and 5 — a date is readable when

## Amendments (plan 05-21)

Plan 05-21 closes the colour and empty-axis clauses of UAT gap G-05-9, from the
Phase 5 UI audit's top fix 2 and its large-data observations. The approved text
above is left exactly as it was — every line above this heading still reads as
approved, and each change below supersedes a specific part of it rather than
rewriting it. G-05-9's third clause (charts in one card share a width and fill
it) is NOT closed here; item 4 says who owns it.

1. **Currency plot split (Spacing "Chart plot height", section 5 "symmetric
   domain", section 6 "Currency: zero line at `y = 8 + 80`", and the diverging
   sentence of the Scale rule).** The 160px plot is DIVIDED between the two
   directions in proportion to their extents, instead of being split 80 above and
   80 below. A side's extent is its own largest month, but never less than a
   quarter of the other side's largest month; the plot is 160, so that floor is
   32px and the 14px zero label and bottom label cannot collide. The zero line
   is at `plotTop + round(160 × up extent ÷ (up extent + down extent))`. The
   160px plot, the 192px SVG, the pitch rule, the node budget and the whole
   premium chart are unchanged. *Reason:* measured against a real export, a
   currency that is almost all deposits spent its lower half on an empty band and
   floated a large negative label far from any bar — a chart that spends half its
   height saying nothing. *Honesty, which is the part that matters:* there is
   still ONE linear scale, so the pixels per unit are identical above and below
   the line and a deposit bar and a withdrawal bar of the same amount are the
   same height in every chart. Each currency still has its own scale (D-15), so
   the block caption about not comparing bar heights between charts stays true,
   and D-17's "deposits up, withdrawals down" is untouched — only the line's
   position inside the frame moves.

2. **Y-axis end labels (section 5, the `y-axis labels` clause; Spacing gutter).**
   The top label is the up extent and the bottom label is minus the down extent,
   each with the exact figure in its SVG `<title>` (D-25). They are computed from
   the exact bigint maxima rather than from the model's floats, so a compact
   text such as `1M` still names `1,029,000` in the title. When a side's extent
   came from the quarter rule and not from a month that exists — the bottom of a
   deposits-only currency, say — **the label names that axis value**, because the
   label sits against the hairline the value defines. A reader comparing the
   bottom label with the monthly table is therefore comparing an axis bound with
   a month's figures, and this is stated here rather than left to be inferred.

3. **Chart zero line and hairlines (Color table, "Chart zero line / bound
   lines").** No change to this spec: the contract's `#5f6368` zero line and
   `#dadce0` hairlines were already correct here, and what had drifted was the
   code. The zero line shipped the hairline grey (1.37:1) and the hairlines an
   off-palette `#e8eaed`, and no test checked either. The component now ships
   the declared strokes and both are pinned — a unit test reads this row off the
   contract text and compares it with the stylesheet, and a browser test reads
   the computed strokes on the premium and currency charts. The audit's top fix 2
   is closed by that, and this row is unchanged.

4. **NOT amended here: the pitch rule and the label stride.** Section 6's
   "Pitch rule" and "X axis" clauses stand exactly as approved, and no plan has
   changed them. G-05-9's width clause is a separate question from the axis
   split above: it asks whether charts in one card share a width and fill it.
   Equal widths cannot be had by padding or stretching the frame, because each
   chart's month axis is its own span (D-17, locked to "from the first
   operation") and a stretched frame draws a flat zero line across months that
   are not in the data — which reads as "nothing happened". The user chose, for
   that clause, **a finer integer pitch**: the largest whole pixel up to 16 for
   which `months × pitch ≤ 576`. That is planned as 05-22, which is also the plan
   that amends the pitch rule and the label stride and the one that closes G-05-9
   in full. This plan closes two of its three clauses and records the third here
   so no later reader believes it was overlooked.

### One thing this plan deliberately did not do

The premium chart's short-axis emptiness is untouched. A five-month premium
chart stays narrow, because the pitch is capped at 16, and no plan in this phase
changes that. It is a different question from the currency plot split above —
that one wasted half a 160px plot on an empty band, while this one is a chart
that is simply small.

## Amendments (plan 05-22)

Dated 2026-10-02. Plan 05-22 closes the width clause of UAT gap **G-05-9** — the
last of its three — by the user's choice, made after plan 05-21 was written:
**a finer integer pitch** (option B of the three put to them). As in the two
appendices above, the approved contract is left exactly as it was; each change
below supersedes a specific part of it rather than rewriting it, so the text
above still reads as approved and the reason it changed is on record.

1. **Pitch rule (Spacing rows "Chart bar pitch" and "Chart bar width", and
   section 6 "Pitch rule. Decision").** Pitch is the **largest whole pixel from
   4 to 16** for which `months × pitch ≤ 576`; bar width is `pitch − 1`, so
   **3 to 15px**. The two Spacing rows above are superseded in their value
   columns: `16 / 12 / 8 / 4px` becomes "any whole pixel from 4 to 16" and
   `15 / 11 / 7 / 3px` becomes `pitch − 1`, a 3-to-15px range. *Reason:* a ladder
   of four steps answers in jumps of four, so a month count landing just past a
   step lost most of the plot. Measured on a real export, a 56-month chart drew
   448 of 576px and a 73-month chart 292 of 576px — 50.7% of the column, half
   the width available — and 115 months drew exactly what 116 months did. Under
   the whole-pixel rule the plot is 80.6% to 100% full for every month count from
   37 to 144, 100% wherever the count divides 576, and the worst case is 116
   months at 464px, where the 4px floor takes over. The rationale the original
   decision gave — "the plot always fills the card width as well as possible
   without ever scaling the text" — is now actually true rather than true only at
   36, 48, 72 and 144 months.

2. **Label stride (section 6 "X axis (D-26)").** The first month is labelled,
   then **every 12 months**, or every 24 months — that is, the stride doubles
   below a pitch of 8px, when 12 × pitch would be under the 96px floor. The
   sentence above said "every 24 when the pitch is 4px", which was true for
   every pitch the old ladder produced and is now wrong at 5, 6 and 7. The two
   cases are one whole pixel apart: 12 × 8 is exactly 96 and keeps the narrow
   stride, 12 × 7 is 84 and does not. **24 × 4 is exactly 96**, so labels stay
   **at least 96px apart** at every pitch the model can produce, and a label
   whose text would run past the right edge of the SVG is still skipped. Bar
   width, the tick offset and the focus ring already worked at an odd pitch, so
   no other geometry changed.

3. **Honesty — what did NOT change, and why the widths are not equal.** Each
   chart still spans **its own months**, from the first operation (**D-17**), and
   each currency still keeps **its own scale** (**D-15**), so the block caption
   warning that bar heights are not comparable between charts stays true. The SVG
   is still a fixed size and is **never scaled**, so the axis text stays **14px**
   and no frame is stretched past its data. The widths therefore become
   **near-equal, not equal**: two currencies with histories a few months apart
   now draw almost the same number of pixels, and two with very different
   histories still draw different widths, because that difference is the month
   span and the span is what the axis means.

4. **The options weighed for G-05-9's width clause, and why this one was
   chosen.** A **shared month axis** across the charted currencies would give
   equal widths and a month column aligned down the card, but it amends D-17's
   "from the first operation" — a chart would gain months the export never
   mentions — and it was not chosen. **Frame stretching**, scaling each chart's
   plot to the same width, was rejected: a stretched frame draws a
   **flat zero line** across months that are not in the data, which reads as
   "nothing happened", and it puts the same month at a different value height
   in every chart. **Leaving it as it was** was not chosen either, because half
   a plot answering "nothing happened" is the same complaint in a different
   costume. A finer whole-pixel pitch was chosen: it spends plot width that was
   genuinely unused without touching what a position on the axis means.

5. **Unchanged by this appendix.** The 144-month scroll threshold and the 4px
   floor above it; pitch 16 for up to 36 months, so short charts stay narrow —
   including the five-month premium chart, which is a chart that is simply small
   and is a different question from the currency plot split in the 05-21 appendix
   above; the SVG size formula `56 + months × pitch + 4`; bar width `pitch − 1`;
   the pointer target at the full pitch; and the node budget of
   `3 × months + 40`. The 05-21 plot split, the y-axis label rule and the colour
   amendments are untouched and still in force.

6. **G-05-9 is closed in full by plans 05-21 and 05-22 together.** The colour
   and the empty-axis clauses were closed by the 05-21 appendix above, whose
   item 4 recorded this width clause as "NOT amended here" and named 05-22 as
   its owner; that item is now discharged by this one. All three clauses are
   closed, and no further plan in this phase inherits an open reading of the
   gap.
