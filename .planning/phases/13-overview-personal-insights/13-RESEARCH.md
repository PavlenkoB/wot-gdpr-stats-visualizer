## Summary

The phase replaces the Overview's chips and section cards with a computed insight page. The work splits into four pieces that touch different code. (1) A new `overview` worker channel: it needs a `DataQuery` and `DataResult` variant, a `DATA_FILES` entry, one answer branch and a memo, and it must be field-less. Almost all the plumbing already exists (validator, memo, per-channel supersede in `QueryClient`). (2) A pure insight model. Most of it is reuse: the merged playtime aggregate already stored on the meta record gives the logged-in total, the day and hour arrays and the per-game scopes. The genuinely new inputs are the WoT per-tank and account rows, and one number the aggregate does not carry, the longest session. (3) A bento UI. The fill rule, the container breakpoints and the expand behaviour all have working reference code in the sketch, so this is a port, not a design task. (4) A build-time tank table with a script that calls the WG API. This is the one-way item, and it is gated on a legal reading that I could not complete.

What the worker already keeps is better than the spike suggests. The WoT player-statistics files and the Activity_history session files are not in the new-game family, so they are stored RAW, column for column (`src/lib/worker/ingest.worker.ts` lines 1136-1140 choose `storeFile = storeRows && (!family || ...)`, and `family` is false for them). `BATTLE_LIFE_TIME`, the record and series columns, `XP_AMOUNT`, `DAMAGE_BLOCKED_BY_ARMOR` and `TREES_CUT_COUNT` therefore reach the worker whenever the export carries them. What the worker does not keep: chat and clan rows (the categories are known-deferred, so storage is skipped), Game_Forums rows (deliberately unpromoted), and any per-session maximum (the aggregate keeps bins, not the maximum). The repository has no fixture that carries the record and series headers, so those headers are pinned only by the spike script that ran on the real export. Tests must add them.

Four decisions need the user before planning. The first is a real conflict. D-04 lists "records" among the tiles that SUM across accounts. A sum of "most damage in one battle" across two accounts is not a number any battle produced, so records should take MAX (with the record tank taken from the same account that holds the maximum). Second, D-05 defines "Logged in" across all games, which differs from the spike's WoT-only 280-day figure and from the sketch's copy ("union of WoT session intervals"). Third, the credits definition differs: the spike sums deposits only, while the Finance pane's builder (`buildCurrency`) also counts `income`. Fourth, the habit tiles (streak, busiest day, signature hour, longest session) need a stated scope; the sketch uses WoT sessions. The legal gate (D-07) also needs a human. As relayed by a summarising fetch (not a verbatim read), the Wargaming API Policy asks for a copyright notice and a link to the game's official site in an application that uses API data, and the licence clauses restrict "derivative works" and "commercially distribute" without consent. This is not legal advice and I did not clear it.

**Primary recommendation:** Build the channel and pure model first, with the fixture and oracle tests; run the table script and the Terms gate as a separate blocking checkpoint; port `fillSpans` as a pure module with a parity test against the sketch; and keep pins out of every file the phase8 shell guard bans `localStorage` in. Resolve the four open decisions in the Open Questions section before plan-phase writes tasks.

## Research Focus 1: The `overview` worker channel, end to end

### Current mechanics (verified in source)

- `DATA_FILES` (`src/lib/worker/data-queries.ts`, lines 109-173) is keyed by `Exclude<DataQuery['channel'], 'logins'>`, so adding `'overview'` to `DataQuery` forces a `DATA_FILES.overview` entry at compile time. Each entry is `{ names: Set<lower-cased file name>, categories: string[] }`. Example from lines 124-127: `vehicles: { names: VEHICLE_FILE_NAMES, categories: [CATEGORY_PLAYER_STATS] }`.
- `isDataQuery` (lines 325-353) rejects every field a field-less channel does not own. The rule is `keys.length === 1 && keys[0] === 'channel'` (lines 340-341). The new channel must be field-less, so the validator needs only its name. `DATA_CHANNELS` (line 290) is derived from `Object.keys(DATA_FILES)` plus `'logins'`, so registering the key is enough for the validator to accept it.
- `answerDataQuery` (lines 370-494) is an exhaustive switch with `default: throw new Error('unreachable channel');` (lines 491-493). An `overview` case must be added here, or the default will throw.
- `MAX_MEMO_ENTRIES = 16` (line 508) and the memo key is `channel:JSON(query)` (line 541). The memo entry is valid only for the current `importedAt` (lines 546-553).
- The worker message dispatch (`src/lib/worker/ingest.worker.ts`, lines 124-167): `data-query` goes to `handleDataQuery` (lines 156-159).
- `handleDataQuery` (lines 312-401): validates, then branches `logins` to `answerLogins` (lines 336-339) BEFORE the memo and the `DATA_FILES` lookup. This is the precedent for an answer built from the meta record. The overview needs both meta (for the playtime aggregate) and rows, so it needs the same branch shape.
- `handlePlaytimeQuery` (lines 224-285) shows the rebuild path: a stored aggregate whose `v` is not `PLAYTIME_VERSION` is rebuilt from `readSessionRowData()` and written back with `writePlaytimeIfCurrent` (lines 245-270).
- `QueryClient` (`src/lib/core/query-client.ts`) supersedes per channel (`#supersedeChannel`), so an `overview` ask does not release any other block's question, and vice versa. `handle` settles a channel mismatch as an error.
- The main-thread wiring: `src/lib/import/worker-client.svelte.ts` builds `this.data = new QueryClient(...)` (around line 214) and routes `data-result` and `data-error` to it (around line 599). Dashboard passes the client to child blocks; the Overview currently receives only `result` and `onopen` (`src/lib/shell/Dashboard.svelte` line 387: `<Overview {result} onopen={openPane} />`), so Dashboard must also pass `ingestClient.data`.

### Answer shape and the single-snapshot rule

The answer must come from one read transaction: the meta record, the named rows and the playtime aggregate. Every existing channel's comment states why (`handleDataQuery`, lines 288-311: "the answer and the rows behind it come from the SAME read"). A stale playtime aggregate (`v !== PLAYTIME_VERSION`, or absent) needs a session-row read, which is a second transaction. The playtime path already handles that case by echoing the snapshot's `importedAt` and writing back only when the dataset is still current (`writePlaytimeIfCurrent`, db.ts lines 987-997). The overview branch must do the same.

### Supersede and memo rules

- Supersede is per channel (`QueryClient.query` calls `#supersedeChannel(query.channel)`). Overview asks for one channel only, so Overview never releases the Playtime or Finance questions.
- Memo key is `overview:{"channel":"overview"}`, valid only for the current `importedAt`. `clearDataQueryMemo()` runs on every ingest (line 1422) and every clear (line 658).
- Returning to the Overview is instant from the memo, because the memo is keyed on `importedAt` alone (D-02).

### Field-less validation details

`{ channel: 'overview' }` is the only valid shape. Any extra key (`title`, `battleType`, `game`) must be rejected with the fixed `invalid query` detail. Add `isDataQuery` tests for: the bare query (true); the bare query plus each of `title`, `battleType`, `game` (false); `Object.create({ channel: 'overview' })` style inherited keys (false, because `Object.keys` reads own properties only, line 340 comment).

## Research Focus 2: Stored rows, existing aggregates, and gaps

### Storage fact: what the worker keeps

The import path decides what is stored. For a file in a supported category that is not a new-game family file, the row is stored raw, and only the userInfo sanitiser and the LOGIN/BIRTH_DATE strip touch it (`ingest.worker.ts` lines 1136-1140 and 1240-1248). The relevant facts, quoted from source:

- `src/lib/worker/categories.ts`: `SUPPORTED` includes `'Player_statistics'`, `'Activity_history'`, `'Financial_data'`, `'Payment_history'`. `KNOWN_DEFERRED` is `['Chat_history', 'Clans']` (verbatim).
- `src/lib/worker/new-data-allowlist.ts`: `FAMILY_PATTERNS` covers HEAT, WOTC, WOWP, WOWS crews/storage, the history files and five promoted-folder names. `FAMILY_CATEGORIES` is `'authorized_third_parties', 'bans', 'bonus_codes', 'personal_coupons', 'subscriptions', 'surveys'` (verbatim). None of the WoT files the overview needs is a family file, so their rows are stored unfiltered.
- `src/lib/worker/ingest.worker.ts` `PRESENCE_CATEGORIES` (lines 117-122): `'player_statistics'`, `'financial_data'`, `'payment_history'`, `DEVICE_INFO_CATEGORY`. `activity_history` is NOT in it, so the sessions file has no presence fact (see the gap list).

### What the playtime aggregate can and cannot answer

`PlaytimeSlice` (`src/lib/core/types/worker-messages.ts`) holds: `seconds`, `sessions`, `excluded`, `dayIndex`, `daySeconds`, `daySessions`, `hourOverlap` (168 cells, indexed `weekday * 24 + hourOfDay`, Monday = 0), `hourStart`, and `bins` (12 duration bins). Verbatim from the type's doc: "168 cells indexed `weekday * 24 + hourOfDay`, Monday = 0." `HOUR_GRID_BASIS` is `'overlap'` (`src/lib/features/playtime/playtime-shared.ts` line 41).

- Logged in (all games): `all.seconds`. Merged, so overlap is counted once (`aggregateSlice`, lines 533-571).
- Days in battle, streak, busiest day, years, hour of day: all derivable from the arrays. Streak: consecutive `dayIndex` values. Busiest day: maximum of `daySeconds`. Years: group `dayIndex` through `civilFromDays`. Signature hour: sum `hourOverlap` over the seven weekdays for each hour (`cell % 24`).
- Longest session: NOT derivable. The `bins` array counts sessions per length bin, so it gives no maximum. The longest raw session is `max(end - start)` over usable sessions, and it is not stored.

Two ways to close the longest-session gap:

- Option A (recommended): add `longestSeconds: number` to `PlaytimeSlice`, computed in `aggregateSlice` as the maximum of `end - start` over usable sessions (raw, not merged). Bump `PLAYTIME_VERSION` from `3` to `4` (`playtime-shared.ts` line 64). The existing lazy rebuild path applies (`ingest.worker.ts` lines 245-270). The overview branch must use the same rebuild for a stale `v`. Tests pinned to 3 must move: `tests/unit/import/ingest-worker.test.ts` line 2063 ("PLAYTIME_VERSION is 3, so an aggregate from the previous build is stale") and line 2074 (`expect(PLAYTIME_VERSION).toBe(3)`).
- Option B: read session rows in the overview branch and compute the maximum there. No version bump, but it reads every session row on each first answer per import, and it needs the session-file name predicate (`sessionFileNameGame`, `playtime-aggregate.ts` line 239) in the snapshot reader.

### Gaps: what the worker does not keep or does not compute

1. No longest-session maximum (above).
2. No presence fact for the sessions file. `activity_history` is absent from `PRESENCE_CATEGORIES`, so "Not in this export" for the Time group must come from `playtime.sessionsFileSeen` (in `PlaytimeScope`) and from the presence of the WoT game in `byGame`, not from `files`.
3. No per-tank reducer over WoT vehicle rows. The vehicles builder is a table builder and returns rows per account (`vehicle-aggregate.ts`, lines 824-840: "The rows stay PER ACCOUNT"). The overview needs its own fold keyed by `VEHICLE_NAME`.
4. Chat and clan counts are not stored and need no storage for this phase. Do not add them.
5. Column-level absence is not file-level absence. A file can be present without `DAMAGE_MAX` (older export revision). The tile must show "Not in this export" with the column named, not a zero.

### Account grouping (CR-01 rule)

Every multi-account read keeps the first row's keys per account group (`AccountRowGroup`, `csv-columns.ts`). The vehicle builder does this with `resolvedByGroup` (`vehicle-aggregate.ts` lines 241-246). The overview reducer must do the same: resolve each group's column keys from that group's own first row, and never read one account's cells through another account's keys.

## Research Focus 6: UI implementation risks

### Port `fillSpans` and `gridHoles` exactly

The reference is `.claude/skills/sketch-findings-wot-gdpr-stats-visualizer/sources/overview-final/_shared/model.js`. Its header says the functions are "Pure grid-fill helpers (no DOM, no WG): unit-testable in node via `require`". Its contract:

- `gridHoles(dims, C)`: simulates `grid-auto-flow: dense` for `C` columns. `dims` is `[[colSpan, rowSpan], ...]`. Returns `{ rows, holes, reorder }`. `reorder` is true when dense placement would show a tile before an earlier one (visual order would differ from DOM order).
- `fillSpans(tiles)`: `tiles` is the ordered visible tiles of ONE group. Returns `{ c4, r4, c2 }`: the extra column span for the 4-column layout, the extra row span (always 0), and the extra column span for the 2-column layout. Only feature tiles widen (`if (s === 'feat')`). Heroes stay 2x2 and metrics stay 1x1.
- The sketch's own statement of its verification: "agree in all 309,247 group/pin/column cases (node)" (`sketch/.../overview-insights.md` and the 030 README). That claim comes from the sketch's node run; this research did not re-run it.

Port to `src/lib/features/overview/overview-grid.ts` (pure, no DOM). Keep the algorithm and its names. Write a node oracle test that enumerates the default tile set's pin subsets (the sketch's approach), asserting: no hero or metric widened; no result has more holes than leaving the group alone; `reorder` never true for the chosen result.

### Set spans through CSSOM only

The sketch writes `--span4`, `--rows4`, `--span2` as custom properties and consumes them in `@container` rules as `grid-column: span calc(2 + var(--span4,0))`. In Svelte 5, set them with a `style:--span4={n}` directive or an element action that calls `el.style.setProperty` (see the CSP note above). Do not use a `style=""` attribute.

### Container queries for columns

- `.overview` is the container: `container-type: inline-size`. The measured width is the content box of the Overview root, which sits inside the detail pane. This keeps `DetailPane.svelte` (a shell file) unchanged.
- Breakpoints: `@container (min-width: 880px)` gives four columns; `(min-width: 480px)` gives two; below that, one column with `grid-column: auto` and `grid-row: auto` (spans reset).
- Do NOT use `@media (max-width: 480px)` for these. The phase8 guard requires exactly one `max-width: 480` media block in `app.css`. Container rules do not match that guard's regex.
- Verify the breakpoints at the sketch's widths (1040, 880, 879, 600, 480, 479, 340 px) by reading computed `grid-template-columns` in e2e.
- Browser support: container queries and `:has()` are in Chrome well before the project's Chrome-first target (ASSUMED, see Assumptions A1).

### Expand in place, View Transitions, and Svelte 5

Sketch behaviour to port: the open tile grows downward; siblings keep natural height while a tile is open (`.bento:has(.tile.open){align-items:start}`); x, y and width of the clicked tile do not change; scroll is adjusted so the tile stays under the pointer; the change goes through `document.startViewTransition` when available and `prefers-reduced-motion` is off; intent is recorded synchronously; a 600 ms fallback applies the change if the transition callback does not run; promises are caught because a newer transition can skip an older one.

Svelte-specific notes:

- The DOM update must run inside the transition callback, so the browser's "after" snapshot sees the new state. In Svelte 5, `flushSync` is the usual way to commit synchronously inside a callback (ASSUMED: unverified for this case; see A2). Test it in Chromium.
- Tiles must not be re-created on expand. Use a keyed `{#each}` and toggle a class or `aria-expanded`. Add an e2e probe: set an expando on the tile element before expanding, read it after, and assert it survives.
- Pin and unpin move a tile between groups. Each group is its own `{#each}` and its own grid, so Svelte cannot move the node between blocks. The tile is re-created. Restore focus by tile id after the move (the sketch does this, "focus is restored to the element that had it"). Do not rely on the old node keeping focus.
- Name only the transitioning elements with `view-transition-name`, set through CSSOM, and clear the name after the transition. Two elements with the same name in one snapshot break the transition.
- Callers must not allow a 600 ms fallback timer to apply a stale state after a newer click. Record the wanted state synchronously and let the newest click win (sketch behaviour: "two quick clicks mean open then close").

### Roving tabindex and keyboard

Exactly one tile button has `tabindex="0"`: the last focused tile, initially the first in DOM order. Arrow keys move in DOM order (left/right) and by position (up/down, the tile whose horizontal extent overlaps in the adjacent row, using bounding rects). Home and End go to the first and last tile. Enter and Space expand (native button). Escape closes an open tile and returns focus to it, and must call `preventDefault()`. `DetailPane.svelte`'s document-level Escape handler returns early on `event.defaultPrevented`, which is what stops it from also sending focus to the list. P pins or unpins the focused tile; the tile carries `aria-keyshortcuts="p"`. The star is a real `<button>` with `tabindex="-1"` and a fixed label ("Pin <tile>") and `aria-pressed`. The list pane's j/k handler is on the list element only (`ListPane.svelte` `onNavKeyDown`), so the tile keys do not conflict.

### Live region for pin announcements

The page carries exactly two `[aria-live]` elements on Overview (`tests/e2e/shell/dashboard.spec.ts`, around lines 1074-1078). Do not add a third. Announce pin and unpin through the page-level chart announcer that Dashboard provides by context (`CHART_ANNOUNCE_KEY`). The announced strings carry no data: "Pinned <tile>, 4 pinned" and "Unpinned <tile>, 3 pinned" (sketch behaviour, `tooltip-pin.ts` precedent).

### Pins in localStorage

- Key: one key, for example `wg-export-viewer.overview.pins.v1`. Value: a JSON array of tile ids.
- Read: `try { JSON.parse(localStorage.getItem(KEY)) } catch { defaults }`. - Keep the pin module out of the phase8-banned file list. Put the storage code in `overview-pins.ts` and import the pure functions into the component. The shell's `Overview.svelte` must not contain the literal `localStorage`.
- There is no existing `localStorage` use in `src/` (checked this session). This is the first use, so the pattern is new and the plan should include a unit test with a throwing storage stub.

## Architecture Patterns

### Data flow

```
Import (worker)
  -> meta.playtime (PlaytimeAggregates, unindexed, PLAYTIME_VERSION)
  -> rows: player_statistics, financial_data, payment_history (stored raw); activity_history sessions (stored raw)

Overview mounts (page)
  -> ingestClient.data.query({ channel: 'overview' })      [QueryClient, per-channel supersede]
  -> worker data-query -> isDataQuery (field-less) -> memo(importedAt)?
       miss: one read transaction: meta (+ rebuild playtime if v != PLAYTIME_VERSION) + four named files
       -> buildOverviewView(inputs)  [pure: sums, union, MAX, guards, table lookup]
  <- data-result { importedAt, result: { channel: 'overview', view } }
  -> acceptDataOutcome(outcome, 'overview', askStamp, currentStamp)
  -> overview-state (loading | ready | error)
  -> OverviewBento: fillSpans per group (CSSOM spans) -> tiles (keyed) -> expand / pin / keyboard
  -> overview-pins: localStorage, guarded, written on pin only
```

### Module layout

```
src/lib/features/overview/
  overview-shared.ts          view types (OverviewView, TileResult); no runtime imports
  overview-definitions.ts     tile metadata: id, group, size, pane link, reads (page-safe)
  overview-aggregate.ts       worker-only pure builder (imports the table)
  vehicle-table.generated.ts  committed table, worker-only
  overview-grid.ts            fillSpans / gridHoles port (pure)
  overview-pins.ts            localStorage ids, guarded I/O, pure validation
  overview-state.ts           outcome acceptance and state derivation
  OverviewBento.svelte        groups, grids, absent rows, live announcements via context
  OverviewTile.svelte         one tile: label, value, rule, expand, star
src/lib/shell/Overview.svelte thin composer; keeps data-testid="overview"
scripts/vehicles/build-vehicle-table.ts   generator and --check
```

Keep the feature components out of `src/lib/shell/` except the composer. The phase8 shell guard reads every `.svelte` and `.ts` file directly under `src/lib/shell/` for banned tokens, and it lists `Overview.svelte` by name.

### Worker-side versus page-side split

Send numbers and resolved names over the wire, and format on the page. The view type carries: integers (seconds, counts, battles), ratios as numbers, resolved names (from the table or the tag fallback), a class key from the table, and absent markers. It carries no formatted strings and no account names. This keeps the worker output testable and locale-free, and it limits what crosses `postMessage`. Use arrays of `{ id, ... }` objects, not objects keyed by tile id, so no tile id can reach a prototype (the T-05-09 rule in `data-queries.ts`).

### Tile model

- Ids are stable and namespaced by game: pins store them, so they must survive a dataset replace (D-14). Shared tiles (Logged in) belong to a neutral list, not to WoT (see Open Questions).
- A definition has metadata only on the page (group, size, pane link, `reads`) and a compute function only in the worker. A unit test asserts that every metadata id has a compute entry and the reverse.
- Group order: Pinned first (a derived view, not a group), then Time, Tanks, Records, Totals (D-12 names Totals).
- Hero first in DOM so it leads on the phone.

## Common Pitfalls

### Pitfall 1: A third live region breaks an existing assertion
**What goes wrong:** Pin announcements add `[aria-live]` on Overview, and `dashboard.spec.ts` (around lines 1074-1078) fails.
**Why it happens:** Local announcers are the obvious choice.
**How to avoid:** Use the context announcer that Dashboard provides.
**Warning signs:** `toHaveCount(2)` fails with 3.

### Pitfall 2: Pins cannot live in the banned shell file
**What goes wrong:** `phase8-shell-guards.test.ts` fails on `localStorage` in `Overview.svelte`.
**Why it happens:** The pin toggle is in the component.
**How to avoid:** Put storage in `overview-pins.ts`. The component imports the functions.
**Warning signs:** The guard test's "keeps selection as component state" case.

### Pitfall 3: Tile DOM is re-created on pin, and focus is lost
**What goes wrong:** Pin moves a tile into Pinned. Svelte cannot move a keyed node between two `{#each}` blocks, so the node is re-created and focus goes to the body.
**Why it happens:** Each group is a separate block with its own grid (required for the per-group fill rule).
**How to avoid:** Restore focus by tile id after the change. Do not rely on node identity.
**Warning signs:** A keyboard e2e: press P, then `document.activeElement` is the body.

### Pitfall 4: Escape also moves focus to the list
**What goes wrong:** Escape closes a tile, and `DetailPane.svelte`'s Escape handler then returns focus to the list.
**Why it happens:** The pane listens at document level and only skips `defaultPrevented` events.
**How to avoid:** The tile's Escape handler calls `event.preventDefault()`.
**Warning signs:** After Escape, focus is on the list row rather than the tile.

### Pitfall 5: A dynamic import is a network request
**What goes wrong:** A lazily loaded table or Overview chunk is fetched after load. The zero-network spec counts it and fails.
**Why it happens:** Code splitting is the default habit.
**How to avoid:** Static imports only. Keep the table in the worker chunk.
**Warning signs:** `zero-network.spec.ts` reports a request after the baseline.

### Pitfall 6: Records summed across accounts
**What goes wrong:** Two accounts' "most damage in one battle" are added, giving a number no battle produced.
**Why it happens:** D-04 lists "records" among the tiles that sum.
**How to avoid:** MAX over account groups, and the record tank from the same group as the maximum (Decision 1).
**Warning signs:** A record larger than any single account's record.

### Pitfall 7: Habit tiles mixing scopes
**What goes wrong:** Streak uses the all-games day set, while the sketch uses WoT sessions.
**Why it happens:** `meta.playtime.all` is the default scope.
**How to avoid:** State the scope in the rule line and read the matching scope (Decision 4).
**Warning signs:** A streak longer than the WoT-only streak.

### Pitfall 8: Garage-only vehicles counted as played
**What goes wrong:** Zero-battle rows (kept by the vehicle builder, D-12 there) appear as "most played" or raise "tanks played".
**How to avoid:** Filter `BATTLES_COUNT > 0` for every tank tile.
**Warning signs:** "Tanks played" equals the number of vehicle rows.

### Pitfall 9: Empty and zero record ids
**What goes wrong:** `MAX_DAMAGE_VEHICLE` of `0`, an empty string or `\N` is looked up and shows a random or blank tank.
**How to avoid:** Accept only `/^[1-9][0-9]*$/` as a tank id. Anything else is "vehicle not recorded" (D-09). `\N` for a series means no value.
**Warning signs:** A record tank name of "".

### Pitfall 10: A record tank id that is not in the table
**What goes wrong:** A numeric id resolves to nothing. The spike saw one record id absent from the API.
**How to avoid:** Show "vehicle not recorded". There is no tag to derive a name from.

### Pitfall 11: The currency definition differs from the Finance pane
**What goes wrong:** Credits earned on the Overview disagrees with the Finance pane.
**Why it happens:** The spike sums `deposit` only; `buildCurrency` also counts `income` (`finance-aggregate.ts` line 575: `direction !== 'deposit' && direction !== 'income' && direction !== 'withdrawal'`).
**How to avoid:** Decision 3.

### Pitfall 12: Per-game totals do not sum to the all-games total
**What goes wrong:** The per-game strip adds up to more than "Logged in". This is documented as expected (`buildGameScopes` comment, `playtime-aggregate.ts` lines 663-690).
**How to avoid:** Say so in the strip's rule line, or show only per-game figures.

### Pitfall 13: Inline style attributes are blocked
**What goes wrong:** The sketch's `style=""` attributes violate the policy's `style-src` (the default `'self'` applies, and there is no `unsafe-inline`).
**How to avoid:** CSSOM and `style:` directives only (the ChartTooltip precedent).

### Pitfall 14: A second `@media (max-width: 480px)` block
**What goes wrong:** `phase8-shell-guards.test.ts` requires exactly one such block.
**How to avoid:** Container queries for the grid.

### Pitfall 15: Playtime version bump breaks pinned tests
**What goes wrong:** `ingest-worker.test.ts` lines 2063-2074 assert `PLAYTIME_VERSION` is 3.
**How to avoid:** Update those assertions with the bump, and make the overview branch rebuild a stale aggregate the same way the playtime query does.

### Pitfall 16: Object-keyed views allow prototype keys
**What goes wrong:** A tile id such as `__proto__` writes onto a prototype.
**How to avoid:** Arrays of `{ id, ... }` objects. Maps for lookups.

### Pitfall 17: Removing the chips breaks the "not yet supported" test
**What goes wrong:** `promoted-folders.test.ts` asserts `overviewChips(result).unsupported`.
**How to avoid:** Assert `unsupportedEntries(result).length` instead (Focus 3).

### Pitfall 18: The e2e ceiling is exceeded silently
**What goes wrong:** New specs push the listed count over 273, and the job's `timeout` kills the run.
**How to avoid:** Count after writing (`pnpm exec playwright test --list`), and raise G, W and J together (Focus 5).

### Pitfall 19: The Account card assertions have no tile
**What goes wrong:** The Phase 9 Overview Account card (three e2e tests) has no counterpart in the new design.
**How to avoid:** Decide whether an account tile is kept (Open Questions). Otherwise rewrite the assertions against the list row and the identity header.

### Pitfall 20: The table is not a legal yes
**What goes wrong:** The table is committed before the Terms gate is passed, and the one-way commit cannot be undone.
**How to avoid:** Make the Terms gate a `checkpoint:human-verify` task that comes before the commit task.

```ts
const PINS_KEY = 'wg-export-viewer.overview.pins.v1';
export function readPins(catalog: ReadonlySet<string>, defaults: readonly string[]): string[] {
  try {
    const raw = globalThis.localStorage?.getItem(PINS_KEY);
    if (raw == null) return [...defaults];
    const parsed: unknown = JSON.parse(raw);
    if (!Array.isArray(parsed)) return [...defaults];
    const seen = new Set<string>();
    for (const id of parsed) if (typeof id === 'string' && catalog.has(id)) seen.add(id);
    return seen.size > 0 ? [...seen] : [...defaults];
  } catch {
    return [...defaults];
  }
}
```

```ts
}
```

## Open Questions

1. **D-04: records must SUM or take MAX? (blocking, recommend MAX)**
   - What we know: D-04 lists "records" among the tiles that SUM across account folders. Records are personal bests (`DAMAGE_MAX`, `XP_MAX`, `FRAGS_MAX`, series). The spike rule (`overview-data.md`) says Hall of Fame = records from MAX columns.
   - What's unclear: whether "records" in D-04 was meant to be read as the per-vehicle figures next to it. Summing a per-battle maximum is not a meaningful figure.
   - Recommendation: MAX across account groups, with the record tank from the group holding the maximum. Ask the user to confirm D-04 wording before planning.

2. **Logged in across games or WoT only? (blocking copy and number)**
   - What we know: D-05 says union across all accounts and all games. The spike's 280-day headline was WoT-only, and the spike's per-game figures were smaller. The sketch copy says "union of WoT session intervals".
   - What's unclear: whether the headline is "logged in across all games" or "logged in to WoT".
   - Recommendation: keep D-05 (all games), change the sketch's copy to say so, and show the WoT figure in the Wargaming-life strip. The headline will read larger than the spike figure. Say so in the rule line.

3. **Credits earned: deposits only, or deposits plus income? (blocking definition)**
   - What we know: spike 003 sums `TYPE === 'deposit'` for `CURRENCY_CODE === 'credits'`. `buildCurrency` (Finance pane) counts `deposit` and `income` as in-flow (`finance-aggregate.ts` line 575).
   - What's unclear: whether the Overview should match the Finance pane.
   - Recommendation: match the Finance pane (one definition across the app), and state "credit in-flow" in the rule line. Tell the user the number may differ from the spike.

4. **Habit tiles: WoT scope or all games? (plan decision)**
   - What we know: the sketch's streak, busiest day, longest session and signature hour use WoT sessions. The aggregate has a WoT scope (`byGame`) and an all-games scope.
   - Recommendation: WoT scope for habits, all games for logged-in only, with each rule line naming its scope.

5. **Longest session: add a field and bump PLAYTIME_VERSION, or scan rows? (plan decision)**
   - Recommendation: Option A (field plus bump). It reuses the existing lazy rebuild and avoids reading sessions on each answer. Update the two pinned assertions in `ingest-worker.test.ts`.

6. **D-11 "Logged in always shows" vs D-03 absent rows (plan decision)**
   - Recommendation: when the sessions file is absent, the pinned Logged-in tile shows the dashed "Not in this export" state and stays pinned. It never shows zero. This reads D-11 as "never drops out of Pinned", which the sketch's "pinned absent tiles drop out" rule would otherwise contradict. Confirm with the user.

7. **Terms of Use gate and attribution (blocking for D-07)**
   - The Policy requires a copyright line and a link to the official game site where API data is used. D-07 does not provide for that UI copy. Decide whether to add a footer or about line, and whether a person needs to review the licence before committing.

8. **Phase 9 Account card (plan decision)**
   - The Overview's Account card (Phase 9 D-13) has no tile in the new design. The list row and the identity header keep the multi-account facts. Decide whether an account tile is wanted; if not, rewrite the three e2e tests against the list row.

9. **Default pins: two or three? (resolved by the locked decision)**
   - D-11 gives two. The sketch README gives three (adds "Most damage"). The plan uses two and notes the difference.

10. **Contrast of the heat scale's lightest step (accessibility decision)**
    - The sketch states 2.6:1 for the lightest step. WCAG 1.4.11 asks for 3:1 for meaningful graphics. The sketch's mitigation is the labelled peak and the bar length. Ask the user whether to accept it, or darken the first step.

11. **Requirement IDs (process)**
    - The proposed IDs need registering in REQUIREMENTS.md and the traceability table, and the ROADMAP entry's `Requirements: TBD` needs updating. That is the planner's job.
