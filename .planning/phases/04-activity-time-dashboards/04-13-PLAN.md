## Planner assumptions and flags

- **Why raise the limits and not cut tests or add workers.** Plans 04-11 and 04-12 already reduce the cost that scales worst: the 60,000-session export is imported into a browser exactly once (a shared serial page), every other browser test uses the nine-row fixture, and the zero-network extension uses the 5,000-session preset. Adding workers is ruled out by the recorded ci-e2e-cancel history (one worker is the only configuration that has produced complete CI runs on this runner). What remains is inherent test time, so the limits are what must change.
- **The 5 seconds per new test and the 330 seconds baseline are estimates.** The baseline is the figure the existing config comment gives for the 86 pre-phase tests (about 3.8 seconds each); 5 seconds per new test is a deliberately higher figure because the new tests import an export and some measure layout at two viewports. The margin of 1.3 absorbs the rest. The first CI run replaces the estimate with a measurement (see the truths).
- **JOB_GAP_SECONDS (300).** The non-e2e share of the job: dependency install about 90 s, lint and typecheck about 60 s together, the unit-test step at most 90 s, and the browser install with a warm cache about 60 s. The failure-only report upload is outside that share and small.
- **Trust boundary of the runner.** The workflow runs pull-request code on a self-hosted runner today; a longer job limit widens the window a hung job holds the runner from 10 to 25 minutes but does not change who can run code there (recorded as T-04-26).
