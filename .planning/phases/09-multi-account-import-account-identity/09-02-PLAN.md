## Planner choices (so the executor does not "correct" them)

1. **D-16 order is applied here, not in the classifier.** Years exist only after parsing. The classifier returns roots in code-unit order; the worker computes each root's summary, sorts with `sortAccounts`, sets the legacy `accountRoot` and `identity` from the first account in that order, and stores `accounts[]` already ordered, so replay is identical to import.
2. **No lazy years rebuild for v1.0 caches (recorded as D-22 in CONTEXT.md).** The CONTEXT default "rebuild lazily behind a version constant" is superseded by D-22. A v1.0 cache is always a single-account dataset, and D-13 plus UI-SPEC render one account exactly as v1.0, with no games and no years anywhere. No reader exists for those fields on such a cache, so the summary-version constant, the guarded write and the rebuild tests would be unreachable code. `accountsOfMeta` returns a one-entry list for a legacy meta with empty games and null years, documented as "not computed for v1.0 caches; never rendered for one account (D-22)". Phase 10 decides if a game filter needs them.
3. **D-18 reaches returning caches through plan 09-03 (D-21).** This plan stops NEW imports from storing unknown and known-deferred rows. A v1.0 cache already holds such rows (v1.0 stored every category, including the Game_Forums EMAIL column), and no reader reads them, so D-21 has the worker delete them on load of the cache: an index delete by category in the check-cache path, idempotent, no Dexie bump (D-07, 06-01 precedent), meta untouched. The purge function, its tests and the threat entry T-09-12 live in plan 09-03 Task 3, not here, to keep this plan inside the smart-zone budget. The D-18 test rewrites below are unaffected: they cover the import path only.
4. **Account record.** Built only for a dataset with exactly one account; null for two or more. Plan 09-03 applies the same rule in the lazy rebuild.
5. **Presence cap per account.** `MAX_PRESENCE_FILES` stays 500 but is applied per account, so the flattened top-level list can hold up to 500 times the root count (bounded by the root cap of 32).
6. **`rowIndex` restarts per account and category.** RESEARCH records that no reader reads `rowIndex` and that restarting it per account is safe. It is restarted so that the adjacency edge is real: the same source file from several accounts is stored with the same row indexes, and nothing may key, sort or de-duplicate on `sourceFile` and `rowIndex` alone (D-12). The index is the owning root's running row count for that category plus the row's position in its file.
