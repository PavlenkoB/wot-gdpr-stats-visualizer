# Phase 6 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.
>
> Upstream: D-01..D-17 in `06-CONTEXT.md` are locked and are not re-opened. Spacing scale, the four typography roles plus Caption, the neutral palette, the accent-reserved list, the tile / notice / pill / button / select chrome, the windowed-table pattern, the tooltip, the legend and the copy conventions are inherited from `02-UI-SPEC.md` .. `05-UI-SPEC.md`. Everything this phase adds beyond them is listed under "Deltas from Phase 5" so the checker can audit it in one place. Where CONTEXT or RESEARCH left a choice open, the decision is made here with a one-line rationale (marked **Decision**).
>
> Scope: the **Login history** sub-block inside the `Activity_history` section (replaces the placeholder in `src/lib/shell/LoginHistorySection.svelte`): reveal control, summary tiles, the masked IP table, the country map, the ranked country list, and the city-level opt-in with its city column and ranked city list. Phone-width and touch polish is Phase 7 (section 12 lists what this phase must not break at 375px).
>
> **Out of this document on purpose.** Where the geo data comes from, how the lookup is stored, which thread performs the city download, and the CSP wording are engineering decisions with their own owners (RESEARCH Decisions 1-4). This contract specifies what the user sees and does. For the city opt-in that means the visible states, the copy, the progress, the cancel, and the rule from D-14/D-16 that nothing is fetched before the click; it deliberately says nothing about how the bytes arrive.

Level 0 (`#eef0f2`) is land with no logins; levels 1-5 are countries with logins. The ramp's lightness is strictly monotonic, so darkness alone carries "more logins". Measured on `#ffffff` with the WCAG formula in `tests/helpers/contrast.ts`:

| Level | Token | Value | On `#ffffff` |
|-------|-------|-------|--------------|
| 0 | `--ramp-0` | `#eef0f2` | 1.14:1 |
| 1 | `--ramp-1` | `#b2dcd4` | 1.49:1 |
| 2 | `--ramp-2` | `#7cc7bc` | 1.95:1 |
| 3 | `--ramp-3` | `#43a89c` | 2.87:1 |
| 4 | `--ramp-4` | `#1f7a74` | 5.13:1 |
| 5 | `--ramp-5` | `#0d4f4c` | 9.38:1 |

**Relief rule (explicitly invoked).** Steps 1-3 are below the 3:1 non-text floor on white by design (the same property Phase 4 recorded). Shading is therefore never the only carrier of a value: every country with logins has a tooltip and an accessible name stating its login and IP counts, the collapsible country list gives every number as table text, the summary sentence states the leader, and the legend note states every step's boundary in words. A reader who cannot see the lightest shades loses nothing.

**Scale rule — logarithmic, not rank-based.** Phase 4's heatmaps use a rank-based scale (D-04 there); the map does not. `src/app.css` describes the ramp as rank-based, so this contract states the difference once and the legend repeats it in words. The map's levels are:

```
level(count) = count <= 0 ? 0 : 1 + min(4, floor(4 * ln(count) / ln(max)))     // max === 1 -> every shaded country is level 1
```

`max` is the largest per-country login count. Count 1 is level 1; `max` is level 5. The scale is computed over countries only (never over logins), recomputed when the dataset changes, and levels that no country uses collapse out of the legend (the Phase 4 rule: the legend shows level 0 and the levels in use). Bars or shades are never graded by any other quantity.

## Page Anatomy & Interaction Contract

### 1. Placement and document order (D-04, D-05, D-10, D-16)

The Login history block is the second sub-block of the `Activity_history` card, after Playtime, exactly where the placeholder is today. The `h3` text `Login history` and its style are unchanged. **The Activity card no longer shows `SECTION_NOTE_PENDING` ("Dashboard coming in a later update")**: both sub-blocks are real, so the card's pending note goes away and the e2e assertion at `dashboard.spec.ts:279` flips to `not.toContainText`, like the other ready cards. Section status derivation, the nav, anchor ids and `scroll-margin-top` are unchanged.

**Document order inside the block** (fixed):

```
h3  Login history                                       (existing heading)
  [login-history-status: role=status, aria-live=polite, always in the DOM]
  Reveal row         [Show full IP addresses] + mask-state Caption
  Count tiles        IP addresses | Countries | IPs with unknown country
  Fact tiles         Most-used IP address | Top country | First to last login
  h4  IP addresses
    count line
    login-scroller > login-table
        thead (sticky)

        tbody  windowed rows, one per distinct IP

  h4  Logins by country
```

Heading outline: `h1` -> `h2` section -> `h3` block -> `h4` part. Nothing skips a level. **Focal point:** the three Display-size count tiles are the visual anchor of the block, above the table and the map, as the three totals tiles are for Playtime. The pinned Account record row is a table row, not a heading: its tag and the note under the table carry its label, so there is no `h4` for it.

### 2. State matrices

The block carries `data-testid="login-history"` and `data-state`.

| `data-state` | When | What renders |
|--------------|------|--------------|
| `loading` | Dataset displayed, the login view not yet received | The `h3`, Body `Calculating login history...` in the status line; no controls, tiles, table or map. `aria-busy="true"` on the block |
| `ready` | At least one login row with a readable IP address | Everything in section 1 |
| `no-source` | `Activity_history` has rows but none of the files that carry IP addresses is present (no `*_Game_Sessions.csv`, no `Sessions.csv`, no `Logins.csv`) | The `h3` and Body `This export has no session or login file, so there is no login history to show.` No controls, tiles, table or map |
| `no-usable` | Such a file is present but no row has a readable IP address | The `h3`, Body `No readable IP addresses were found in this export.`, and the excluded pill when its count is above 0. No controls, tiles, table or map |
| `error` | The worker query or aggregation failed | The `h3` and the destructive-chrome message (copy below), `role="alert"` with no `aria-live` attribute. No retry button: dropping the export again is the retry and the dataset on screen is unchanged |

A stale answer is never displayed: the view carries the `importedAt` it describes and another dataset's answer is treated as no answer (the Phase 4/5 pairing). **Decision**, rationale: the Account record row is shown only in `ready`; in `no-source` and `no-usable` the state line is the whole block, because a lone row with no table around it would have nothing to be a row of.

**`city-optin`** (`data-testid="city-optin"`, `data-state`):

| `data-state` | When | What renders |
|--------------|------|--------------|
| `idle` | Default; also after cancel, after an error, and after a dataset replace or Clear | `h4`, the intro Caption with the size, and the **Load city-level detail (~N MB)** button. Nothing has been fetched |
| `downloading` | The button was pressed | `h4`, a Body progress line `Downloading city detail: {x} of {y} MB`, a determinate `<progress>`, and a **Cancel download** button (Delta 11). The Load button is not rendered |
| `decoding` | The bytes are in and the lookup is being prepared | `h4` and Body `Preparing city detail...` with an indeterminate `<progress>`. No Cancel (the step is brief and not interruptible) |
| `ready` | The lookup finished | `h4`, Body `City detail loaded from DB-IP ({YYYY-MM}). The City column is now in the table above.`, the accuracy Caption, and the city list. The Load button is not rendered; there is no unload control |
| `error` | The download or decode failed, or the file failed its checks | `h4`, the destructive-chrome message (copy below, `role="alert"`, no `aria-live`), and the Load button again so the user can retry. The country view is unchanged |
| `cancelled` | The user pressed Cancel | `h4`, a neutral-info line `City-level download cancelled. Nothing was kept.`, and the Load button again |
| `unavailable` | This build ships no city asset (local or PR builds) | `h4` and a neutral-info line `This copy of the page does not include city-level data.` No button, nothing fetched |

**Decision (RESEARCH Decision 7), rationale:** when the build carries no city asset the button is hidden and one sentence says why, because a button whose size label cannot be computed and whose click can only fail is worse than no button.

**Decision (cancel vs error), rationale:** D-14 says cancel or failure leaves the country view intact with a visible message. Cancelling is the user's own choice, so it gets the neutral-info chrome; only a real failure gets the destructive chrome.

**Decision (RESEARCH Open Question 3), rationale:** a dataset replace or Clear returns `city-optin` to `idle` and removes the City column and the city list, in step with the mask reset (D-07), so the page never shows city detail the user has not asked for about the dataset in front of them. A download or decode in flight at that moment is cancelled silently (no cancelled line is shown, because the user did not press Cancel). Whether the next click is instant because the decoded lookup is still in memory is invisible to the user and is the planner's call; the button copy and states are the same either way.

Focus after a state change: leaving `downloading` for `ready` moves focus to the ready Body line (`tabindex="-1"`); leaving it for `cancelled` or `error` moves focus to the Load button; pressing Load moves focus to Cancel. Focus is never left on an element that has just been removed.

### 3. Reveal control and the IP table (ACTIVITY-05, D-04..D-08)

**Reveal row.** `display: flex; flex-wrap: wrap; gap: 8px 16px; align-items: center`. One native `<button type="button" data-testid="login-mask-toggle">` in the Phase 3 `bar-button` chrome (Label 14/600, `padding: 8px 16px`, `1px solid #80868b`, bg `#ffffff`, text `#3c4043`, radius 6px, hover bg `#f1f3f4`, accent focus ring), then the mask-state Caption.

**Decision (a11y pattern), rationale: label swap, not `aria-pressed`.** The button's visible text is `Show full IP addresses` while masked and `Hide full IP addresses` while revealed. It carries **no** `aria-pressed`, so a screen reader announces one change, not two. `data-masked="true|false"` is the test hook. Pressing it announces the new state in the status region (`Full IP addresses are now shown.` / `IP addresses are now masked.`). The announcement never contains an address. Focus stays on the button.

The Caption beside it reads `IP addresses are masked: the last part of each one is hidden.` while masked, and `Full IP addresses are shown. Hide them again before sharing your screen.` while revealed.

**Mask lifecycle (D-07).** One rune. Masked on every load. Reset to masked on a dataset replace and on Clear. Not persisted anywhere (no storage, no URL). It is **one derived display function** (`displayIp(row, revealed)`) that every surface below reads, never a CSS toggle over two strings: the DOM holds only the string being displayed.

**Mask surfaces (D-07's list, surface by surface).** The invariant is that while masked, no unmasked address exists anywhere in the DOM, in any attribute, in the accessibility tree, in the selection, in the clipboard, or in the document title.

Counts and shares cover login rows only. **Decision (RESEARCH Pitfall 11), rationale:** a login is one session row, and when an export carries both a `Logins.csv` and session files its rows are **both counted** (no de-duplication by timestamp, D-01), so the totals can be higher than the account's real login count; a Caption under the count tiles says so only in that case: `This export lists logins in more than one file, and each file's rows are counted.`

**Date display (RESEARCH Decision 8).** **Decision, rationale:** `First seen`, `Last seen` and the range tile show the **date only, `YYYY-MM-DD`, taken from the wall-clock fields as written**, with no timezone conversion (D-03, Phase 4 D-01). Two source formats in one column (`14.03.2013 14:30` and ISO) would read as a bug, and the time of day adds nothing to a history of where the account was. The underlying ordering uses the full parsed timestamp. A row whose timestamp cannot be read still counts as a login and is simply excluded from first and last; an IP with no readable timestamp shows `—` with hidden `no readable date`.

**The table (D-05).** A native `<table data-testid="login-table">` inside `<div data-testid="login-scroller" role="region" aria-label="Login history by IP address" tabindex="0">` with `overflow: auto` and `max-height: 480px`. One row per **distinct full IP address** (not per session, not per run). Two masked rows can look identical; that is expected and the group key is the full address. The count line above reads `{n} IP addresses · {l} logins` (`1 IP address`, `1 login`).

Columns, in order: `IP address`, `Country`, `Logins`, `First seen`, `Last seen`, `Games`, and `City` after opt-in (section 5). Widths per the Spacing exceptions table.

- **`<thead>` is sticky** at `top: 0` of the scroller, 40px, surface `#f7f7fa`. Each header is `<th scope="col" aria-sort="ascending|descending|none">` containing one `<button data-testid="login-sort-{key}">` that fills the cell, copied from the Phase 5 header (Label `#5f6368`, transparent, 40px tall, `padding: 0 8px`, hover bg `#dadce0` with text `#3c4043`, accent focus ring). The sorted header shows an `aria-hidden` arrow (`↑` / `↓`) and the `#f1f3f4` surface. Keys: `ip`, `country`, `logins`, `first`, `last`, `games`, `city`.
- **The first column (IP address) is sticky** at `left: 0` (bg `#ffffff`, header cell `#f7f7fa`, 1px right border `#dadce0`, the corner above both axes), because the table scrolls horizontally inside its scroller and a row that has lost its address is unreadable.
- **Decision (horizontal scroll at 720px), rationale:** the six default columns total 720px against the 638px card, so the table scrolls sideways even on desktop. D-05 fixes the six columns and the column set cannot shrink; the order puts the figures a reader wants first (IP, Country, Logins, First seen, Last seen all land within the first 584px), the sticky IP column keeps identity, and the scroll stays inside the scroller (never the page).
- **Sorting.** Default sort `Logins` descending (D-05). First click on a new column sorts descending for `Logins`, `First seen`, `Last seen` and ascending for `IP address`, `Country`, `Games`, `City`; clicking the sorted header flips the direction; there is no unsorted state. Ties break by the full canonical address ascending (numeric by address bytes, IPv4 before IPv6), never by locale. `IP address` sorts numerically by the address. `Country`, `Games` and `City` sort by the displayed text in plain code-unit order (never `localeCompare`: the Phase 4/5 rule). Special values (`Unknown country`, `not recorded`, `—`, `City unknown`) always sort **last**, in both directions. A sort change scrolls the scroller to the top. The pinned Account record row is **not sorted** and stays first.
- **Decision (RESEARCH Open Question 5), rationale: the IP column is sortable while masked.** Sort order exposes only the relative order of the hidden last part among addresses that already share a visible prefix, which is negligible against the shoulder-surfing threat masking addresses; and disabling it would make the table reorder under the user's hands whenever they toggle the mask on a table sorted by address.
- **Pinned Account record row (D-02).** When `Account_Info.csv` has an IP, a **separate `<tbody data-testid="login-account-row-group">` placed before the windowed body** holds one row (`data-testid="login-account-row"`, bg `#f7f7fa`): the IP cell follows the mask (`displayIp`); the Country cell shows the account file's country **as recorded** (a two-letter code is shown as its English name through `Intl.DisplayNames`, anything else as written; blank `not in export`); the Logins, First seen and Last seen cells read `—` with hidden `not counted as a login`; the Games cell holds the **Account record** tag; the City cell (after opt-in) shows the recorded city as written, blank `not in export`. It is never counted in a tile, the map, a list or the count line, and it follows the mask like every other address. An address that does not parse shows `not readable`; a blank one `not in export`.
- **Decision (RESEARCH Open Question 2), rationale: the label claims "as recorded", and recorded wins.** This row is Wargaming's own statement about the account, so it is shown as written and **never re-resolved** through the offline table; if the recorded country and the table's resolution of the same address disagree, both are right about different things, and the note under the table says which one this row is.
- **Windowing (D-05).** Only the rows intersecting the scroller (plus 6 rows of overscan each side) are in the DOM, between two spacer `<tr aria-hidden="true">` rows. Spacer heights and the table's minimum width are written through the CSSOM (`element.style.height` / `element.style.minWidth`), never a `style` attribute and never a Svelte `style:` directive (the CSP forbids inline styles and `svelte/no-inline-styles` is an error). **Decision, rationale: window always, with no threshold.** The cost is the same ~30 DOM rows whatever the count, and a threshold is a branch that can be wrong. Rows are a fixed 40px.
- **Accessible structure.** `aria-rowcount` = listed rows + 1 (header) + 1 (the Account record row when present); every rendered row has `aria-rowindex` (header 1, Account record 2 when present, windowed rows after it). Native table semantics, no `role="grid"`. The region is the one focus stop for scrolling. `<caption class="visually-hidden">` repeats the region's name.
- **Cells.** Caption, `padding: 0 8px`, `vertical-align: middle`, `white-space: nowrap; overflow: hidden; text-overflow: ellipsis` **except** the IP cell, which wraps: `white-space: normal; overflow-wrap: anywhere; line-height: 1.4; max-height: 40px; overflow: hidden`. An IPv4 address is one line; a full IPv6 address wraps to at most two lines inside the fixed 40px row (see the width derivation under Spacing) and is never ellipsised, so a revealed address is always fully readable. The `Country`, `Games` and `City` cells are single lines, ellipsised, and carry their full text in `title` (a name or a list of game names, never an address) so a truncated value stays readable. Numbers are right-aligned with `font-variant-numeric: tabular-nums`.
- **Cell values.** `IP address`: `displayIp`. `Country`: the English name through `Intl.DisplayNames(['en'], { type: 'region' })`, guarded (the code `ZZ` and any malformed code never reach it); an address with no country match reads `Unknown country` (D-08), muted. `Logins`: exact grouped number. `Games`: the game names in fixed order `WoT`, `WoT Blitz`, `Warships`, `Warplanes`, joined by `, `; `not recorded` (muted) for an address that appeared only in a file that names no game. `City`: `{City}, {State}` as written (just `{City}` when the state is blank); `City unknown` (muted) when the database has a country but no city; `—` for an address with no country.
- **Notes under the table (all Caption).** Keyboard hint, reused verbatim from Phase 5: `Focus the table, then use the arrow keys or Page Up and Page Down to scroll.` Find-in-page hint: `Only the rows on screen are loaded into the page, so your browser's find cannot see the rest. Sort a column to bring other rows to the top.` The Account record note (only when the row exists): `The Account record row is the address stored in your account details, shown as recorded. It is not counted as a login and is not on the map.`
- **Excluded pills (D-06, RESEARCH Pitfall 2/3).** Through the reused `ExcludedNotice`, directly under the notes, never rendered at zero: pill `1 login row without a readable IP address` / `{n} login rows without a readable IP address`, explanation `Rows whose IP address is blank or cannot be read are not counted in any figure here and are never shown.` Unreadable and malformed addresses are never displayed, not even masked. If the export has more distinct addresses than the table keeps (the cap), a second line, only above zero, states them: `{m} more IP addresses ({k} logins) are counted in the totals but not listed in the table.` **Decision, rationale:** the cap exists to bound memory against a hostile archive; whatever it folds away must stay visible as one honest count so the listed rows and the stated totals never silently disagree. Where such logins land in the country figures is the planner's call (see UI Considerations, unresolved row).

### 4. The country map (ACTIVITY-06, D-08..D-11)

**Basis.** `h4` `Logins by country`. Aggregation is **per country** and the SVG's node count is independent of the number of logins (D-09). Countries come from the offline lookup done at import; no coordinate, address or login row reaches this component.

**Summary sentence (D-10, Body, under the `h4`).** `Logins came from {c} countries. {Country} had the most, with {n} of {t} logins ({p}%).` Singular forms: `Logins came from 1 country.`; when one country holds everything `All {t} logins with a known country came from {Country}.` `{t}` is **all counted logins** (the same denominator as the Top country tile, so the two percentages on screen always agree, including when some addresses have no known country); `{p}` is the whole-percent rule above. The single-country form names its own base (`with a known country`) and is followed by the unknown-country sentence when one applies. When unknown-country addresses exist, append ` {u} IP addresses ({l} logins) have no known country and are not on the map.` (`1 IP address (1 login)`). When **no** address resolved (`no-countries`), the h4 stays and the sentence is replaced by `No login IP addresses could be matched to a country, so there is nothing to show on the map.`; the map, legend, attribution and list are not rendered. (Unknown-country counts are on the count tile in that case.)

**The map.** `<div data-testid="login-map-frame">` (frame chrome in Spacing) containing one `<svg data-testid="login-map" viewBox="0 0 960 500" role="group" aria-label="World map of logins by country">`:

- One `<path>` per country shape. A country with logins carries `class="level-N"` painting `fill: var(--ramp-N)`; a country without carries level 0. Stroke per the Spacing exceptions. Antarctica is not drawn. Countries with logins **and a drawable shape** carry `data-testid="login-country"` with `data-iso`, `data-logins`, `data-ips`, `data-level`; countries without logins are `aria-hidden="true"`, not focusable, and have no tooltip.
- Countries too small to see (`tiny`) that have logins also get the marker circle and the hit circle from Spacing, still **one per country**, never per login.
- Countries that have logins but no drawable shape (about 15 codes in the shipped map) are never on the map; they are reachable through the list and counted in the "not drawn" line.
- **No text of any kind** inside the SVG (section 3, map labels).
- **Decision (scaling), rationale:** the SVG has no text, so `width: 100%; height: auto` cannot make anything illegible; the Phase 4/5 "never scaled" rule exists to protect 14px axis text and does not apply. At 375px the map is a 295px-wide overview and the ranked list is the primary path (section 12).

**Interaction.**

| Input | Behaviour |
|-------|-----------|
| Pointer over a country with logins | Tooltip anchored at the **pointer position** (a zero-size anchor, because the bounding box of a large or oddly shaped country can centre far from the part being pointed at); the overlay ring is drawn on that country; pointer leave closes both |
| Tab | **One tab stop for the whole map** (roving focus, the Phase 5 chart pattern). Tab enters on the highest-ranked country that has a drawable shape (then the last-focused country) and leaves on the next Tab; countries are never individual tab stops. **Decision, rationale:** a hostile or very travelled export can have 200 countries, and 200 tab stops would trap a keyboard user |
| Left / Up arrow, Right / Down arrow | Previous / next country with logins **and a drawable shape, in ranked order, most logins first** (countries with no drawable shape are skipped; they are reached through the list) (ties: English name ascending, code-unit order); stops at the first and last. **Decision, rationale:** spatial arrow navigation across an irregular map is unpredictable; the ranked order is the same order as the list and as the summary sentence |
| Home / End | First / last in the ranked order |
| Keyboard focus | Overlay ring on the focused country; tooltip anchored at that country's centroid point (a zero-size anchor) |
| Escape | Hides the tooltip without moving focus |

A Caption hint above the map reads `Use the arrow keys to move between countries, most logins first.` The tooltip is the shared `ChartTooltip` contract (Phase 4 section 8, Phase 5 section 8) unchanged: `position: fixed`, flip below near the top, 8px clamp from viewport edges, CSSOM-only placement, no delay, no transition, no arrow, non-interactive, dismissible without moving the pointer. It is a **third instance** (`testId="map-tooltip"`); the existing `chart-tooltip` and `finance-tooltip` ids are untouched. Line 1 `{Country}`; line 2 `{n} logins · {m} IP addresses` (`1 login`, `1 IP address`); **no extra lines and never an address**.

**Accessible structure.** The `<svg>` is `role="group"` with the label above. Each country with logins is `role="img"` with `aria-label="{Country}: {n} logins from {m} IP addresses"` (`1 login`, `1 IP address`) and a roving `tabindex` (`0` on the current country, `-1` on the rest). Tooltip, shading and overlay ring are `aria-hidden`; the same two figures are in the accessible name, the tooltip and the list.

**Legend (D-09).** The reused `ChartLegend` (`data-testid="map-legend"`): `Less`, one swatch for level 0 and for each level in use, `More`, then the note on its own line: `Shading is logarithmic, so each darker step covers a wider range of logins. Steps start at {a}, {b}, {c}, {d} and {e} logins.` Step starts are `ceil(max^((L-1)/4))` for each level `L` in use, grouped with the viewer's locale, with duplicates collapsed and the list shortened to the levels in use (`Steps start at 1 and 8 logins.`). When `max` is 1 the note is `Every shaded country has 1 login.`. Swatches are `aria-hidden`.

**Attribution (D-11).** One Caption line directly under the legend, always visible whenever the map is: `<a href="https://db-ip.com" rel="noreferrer noopener" target="_blank" data-testid="map-attribution-link">IP Geolocation by DB-IP</a>, licensed under CC BY 4.0.` The link is `#3c4043` and underlined, with the accent focus ring. It is a user-initiated navigation, not a request made by the page. The same line covers the city data. It lives in `data-testid="map-attribution"`.

**Not-drawn line.** Only above zero, Caption, under the attribution: `{k} countries in the list below are not drawn on the map.` (`1 country in the list below is not drawn on the map.`)

The list is not windowed (at most about 250 rows); it is the guaranteed route to every value for small countries, unshaded-for-sight readers and keyboard users. Rows are not interactive.

### 5. City-level detail (ACTIVITY-07, D-13..D-16)

**Intro (`idle`, Caption).** `Add the city for each IP address. This downloads a database of about {N} MB from this site when you press the button. Nothing is downloaded until then, and nothing from your export is sent with the request.` `{N}` is the file size from the build-time manifest, rounded to a whole number of megabytes (minimum 1), through `formatNumber`.

**Button (the phase's one real action).** `<button type="button" data-testid="city-load">Load city-level detail (~{N} MB)</button>`, the same neutral chrome as the reveal button. **Decision, rationale:** accent blue is reserved for the importing action; a download the user may or may not want is a secondary action, so it is neutral (the Phase 2/3 rule that only the page's primary non-destructive action is accent).

**Downloading.** A Body line `Downloading city detail: {x} of {y} MB` (one decimal, locale grouping; `{y}` is the manifest size, `{x}` the bytes received so far), a native `<progress data-testid="city-progress" max={total} value={received}>` that fills the row, and `<button type="button" data-testid="city-cancel">Cancel download</button>` (the same neutral chrome; Delta 11 amends the contract's original `Cancel`). The progress bar has an accessible name `City detail download progress`; it is not itself a live region (the status region announces the state change, not every percent). If the total is unknown the bar is indeterminate and the line reads `Downloading city detail...`. Pressing Cancel stops the download and returns the block to `cancelled`. No animation or transition on the bar.

**Decoding.** Body `Preparing city detail...` and an indeterminate `<progress>` with the accessible name `Preparing city detail`.

**Ready.**
- Body `City detail loaded from DB-IP ({YYYY-MM}). The City column is now in the table above.` (`{YYYY-MM}` is the data month from the manifest).
- Caption (accuracy, always shown with city data): `City locations are estimates from a public database. They often point to an internet provider's location rather than your own.`
- **The City column** is added at the end of the IP table (section 3) and is sortable; sorting by it works like `Country`. The map stays country-level (no per-login markers, D-16).
- **Ranked city list.** A native `<details open data-testid="city-list">`, summary `Cities by logins`, containing a native `<table>` in a `max-height: 320px` scroller: columns `City`, `Country`, `Logins`, `IP addresses`; one row per distinct place (city, state and country) in ranked order (`data-testid="city-row"`), ties broken by city then country in code-unit order. **Decision (RESEARCH Open Question 4), rationale:** the list is capped at **50 rows**, with a Caption beneath, `and {k} more cities not listed`, when it is cut, because a large export can map to thousands of places and an unbounded list is the one place in this phase whose node count would follow the data. Places with no city name are not rows; they are counted in a Caption `{n} IP addresses have no city in the database.` (only above zero). Unknown-country addresses are not in this list.

**Error (destructive chrome, `role="alert"`, no `aria-live`).** `City-level detail could not be loaded. Your country view is unchanged. You can try again.` A failed download, a corrupt file and an unsupported browser all show this one fixed sentence: it never echoes a system message, a path or a status code. The Load button is shown again beneath it.

**Cancelled (neutral-info).** `City-level download cancelled. Nothing was kept.`

**Unavailable (neutral-info).** `This copy of the page does not include city-level data.`

**Rules (D-14, D-15, D-16).** Nothing is requested before the button is pressed; pressing it makes exactly one request for one same-origin file, and no part of your export is part of it. The result is session-only: it is never stored, a reload returns to `idle`, and Clear has nothing extra to wipe. Cancelling, failing, or leaving the page at any time leaves the country view exactly as it was. The block never claims precision beyond the accuracy Caption.

### 9. Accessibility (summary)

- Every state is stated in visible text; colour only reinforces. Map numbers are available as the summary sentence, the tooltip, each country's accessible name and the country list; table numbers are cell text.
- One new explicit live region: `<p data-testid="login-history-status" role="status" aria-live="polite" aria-atomic="true">`, present in every state of the block, empty (visually hidden with the clip pattern, not `display: none`) when nothing is happening. It carries `Calculating login history...`, the two mask announcements, `Downloading city-level detail.`, `City-level detail loaded.` and `City-level download cancelled.`. The city error uses `role="alert"` **without** an `aria-live` attribute and is not repeated in the region, so it is announced once. The block-level error likewise.
- Tab order follows document order: reveal button, the table's sort buttons left to right, the scroller, the map (one stop), the country-list summary, the city button or Cancel, the city-list summary and the DB-IP link in its place under the legend.
- The reveal control is a native button with a label swap and **no** `aria-pressed` (section 3).
- Untrusted text (IP strings, country codes and names, city names, titles) is rendered by plain interpolation only: no `{@html}`, wrapped or ellipsised, never placed in a `data-*` attribute that a selector concatenates.
- Privacy: no email, no account `LOGIN`, no nickname and no raw address string appears in any string, attribute, tooltip, `title`, `aria-label`, test id or the document title in either mask state beyond what section 3's table allows while revealed.

### 10. Data and worker constraints the UI depends on

Not visual, but the contract assumes them:

- The worker remains the only Dexie owner and the only place raw rows exist; the main thread receives one compact login view (per distinct IP, per country, per city once loaded), never raw rows or per-login data.
- Every answer carries the `importedAt` it describes; a request or answer for an older dataset is superseded, not rendered.
- A bug in an aggregate must never cost the user their import: a failed aggregate renders the block's `error` state and the dataset on screen is unchanged.
- The city size and data month shown in the UI come from a build-time manifest; if it is absent the block shows `unavailable`.

### 11. Page-wide invariants

- No request is made by this block before the city button is pressed; the zero-network check stays green through import, reveal, sort, map interaction and the country list.
- No new runtime dependency. No inline style attribute anywhere; every dynamic size is an attribute, a class or a CSSOM write.
- The page-wide explicit `aria-live` count is **four** (section 9).

### 12. Phone width (375px) — must not break, polish is Phase 7

`main` content is 327px and a card's inner width is 295px. Required: no page-level horizontal scroll (`document.documentElement.scrollWidth <= 375`). Touch-target sizing (44px), touch tooltips and any map zoom are Phase 7 and must not be precluded: the tooltip is one shared element fed by an active-country state a tap can set, and countries are addressed by `data-iso`.
