<objective>
Close UAT gap G-01-20: a real export wrapped in an extra top-level folder, or re-zipped with its category folders directly at the top level (no account-ID folder), currently shows the generic failure banner instead of classifying correctly. Root cause (see `.planning/debug/wrapped-export-classify.md`): `detectRoot()`/`categoryFoldersUnder()` assume a single, fixed nesting depth — the account-ID folder is always exactly the first path segment, categories always exactly one level below it. This was a known, planner-flagged limitation (01-03-PLAN.md FA-01-03-3, "reversible") that the project owner has now chosen to fix rather than keep accepting.

The fix is additive and confined to `src/lib/worker/classify.ts`'s pure functions: when the normal single-level detection finds a root whose only child is itself unrecognized, retry one (bounded, N-level) layer deeper before giving up; when there is no single first segment at all, but the top-level segments themselves already look like real category folders, treat the archive root itself as the account root. `src/lib/worker/ingest.worker.ts` and the worker message contract are confirmed correct and unrelated (per the debug session) and are not touched.

Purpose: IMPORT-02 ("no fixed layout or naming assumed") and IMPORT-05 ("a valid zip with no recognizable Wargaming structure" still fails, but a valid zip that IS a Wargaming structure — just nested or flattened differently — must now succeed). After this plan, a user whose export got wrapped in an extra folder (a very common thing to do when re-zipping a downloaded archive) or whose re-zip tool flattened the account-ID folder away sees the same categorized results view as a normal single-root export, instead of the generic failure banner.
Output: hardened `src/lib/worker/classify.ts`, two new regression fixtures in `tests/fixtures/export-fixtures.ts`, and their coverage in `tests/unit/classify.test.ts`.
</objective>
