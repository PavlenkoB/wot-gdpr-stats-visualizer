## Decisions made by the planner (record them in the SUMMARY; the requester can override)

1. **Login tiles: the rule, not a bug. Keep the counting, move the label next to the table.** Measured on the running dev server (1280x800, sample export from `buildSampleExport()`): `login-tile-ips` 2, `login-tile-countries` 0, `login-tile-unknown` 2, `login-tile-top-country` a dash with hidden text, both `login-row` rows read `Unknown country`, and the pinned `login-account-row` reads `United States` with the `Account record` tag. The two login addresses are TEST-NET addresses that resolve to no country, so 0 countries and 2 unknown is the correct answer; the Account record's country is the account file's recorded value (Phase 6 D-02, 06-UI-SPEC "never counted in a tile, the map, a list or the count line", and the `loginTiles` docstring). Counting it would also break the invariant that tile logins equal the map's logins. The tag IS on screen at 1280 (x 1082 to 1199 inside a scroller that ends at 1240). What is out of reach is the sentence that explains the row: `login-account-note` sat at y 825 under a 800px viewport, below the table, the keyboard hint and the find hint, while the tiles were at y 292. So the fix is placement: the existing note moves to directly above the table. This departs from the 06-UI-SPEC "Notes under the table" placement, so it is recorded in Amendment A-3. Rejected alternative: count the Account record in the tiles (violates D-02; the requester can override only by also amending Phase 6).
2. **Keyboard lag: not reproducible on a loaded export; the review script sent keys into the empty state.** The review's script waited on `[data-testid=list-pane]`, which exists in the empty state, so its first `j` ran before the import landed. With nothing loaded the selection is pinned to Overview by design (`resolveSelection` returns Overview for a null result, documented in the ListPane handler and in the existing (empty-state) test), so `j` moved focus while `aria-current` stayed on Overview; the import then landed and reset the selection to Overview (Phase 8 D-03); the following ArrowDown stepped from the focused row (Playtime) and selected Login history. Reproduced both ways at planning time: the review script as written gives that exact signature, and the same script waiting for `[data-testid=identity-header]:not([data-variant=skeleton])` gives `aria-current` equal to the focused row after every key at 1280x800, 800x900 and 375x812. So `ListPane.svelte` already sets the selection from the newly focused row in the same handler (`onselect(next, 'keyboard')` runs before the focus move) and the CR-01 stepping from the focused row is intact. The task therefore adds the strict per-key assertions the requester asked for and changes `ListPane.svelte` only if they go red. A possible follow-up, NOT done here because it is outside the three findings: when the first import lands while focus sits on a list row other than Overview, the selection resets to Overview and focus stays where it was.
3. **Phone-rule mechanism: `.shell`-prefixed global selectors on each component's own unique hook, strictly more specific than the scoped rule they replace.** The components' own comments say why the rules were split ("a scoped rule outranks the global one"): Svelte adds a hash class to every scoped selector, so a bare `.headline` or `dd` in app.css loses to the component's base rule, and the relative order of the two stylesheets in a bundle must never decide the outcome. Class and element names also collide across components (`.row` is in ListPane, DurationList and two legends; `.headline` is in ListPane, Overview and SpendSummary; `.label`, `.section-title`, `.count`, `dd`, `section`, `ul`, `li` likewise), so every moved selector is namespaced by a unique ancestor. Recipe: `.shell` + the component's unique hook + the original selector, which is at least one class higher than the scoped original. Where the original already carried a global ancestor (the ListPane import-region button rule is written with a global descendant and already has the specificity of `.pane-list button:not(.row)` plus the hash class), the recipe selector may come out equal to the original rather than higher; that is acceptable only if it is still strictly above every scoped rule it overrides, which the production-to-production snapshot checks. Hooks that already exist: `.pane-list` and `nav` (ListPane), `.pane-detail` (DetailPane), `.overview` (Overview), `[data-testid='identity-header']` and the unique classes `.nickname`, `.skeleton-title`, `.fallback-title` (IdentityHeader), `.phone-bar` and `.phone-title` (DetailPane), `[data-testid='duration-chart']` (DurationList), and `section[data-testid^='dashboard-section-']` (DashboardSection). `PlaytimeSummary` and `LoginSummary` both use the root class `summary`, which also exists in Overview and ImportSummary, so each gets a new unique class token on its root element (`playtime-summary`, `login-summary`); that is a class-attribute-only markup change. One rule must NOT take the recipe: the ListPane `.row` background, which in the old cascade lost to `.row:hover` and `.row[aria-current]` (both one class higher than a plain scoped `.row`); a recipe selector would tie with them and let source order flip the selected and hover highlights on the phone. That one is written with exactly one type selector of extra specificity (`.pane-list li .row`) so it still beats the base `.row` and still loses to hover and selected. The snapshot step in Task 2 is the arbiter for every case.
4. **Empty-state heading to ink: done.** It is trivial and unpinned: `.skeleton-title { color: var(--muted) }` in `IdentityHeader.svelte` is the only thing making it muted, no test asserts that colour, and Phase 3 D-24 requires the skeleton to be distinct from the loaded header by its words and prompt, not by the title colour. The prompt line under it stays muted. The code comment that says the muted title carries the state is rewritten.
5. **One UI-SPEC amendment.** `.planning/phases/08-master-detail-ui-redesign/08-UI-SPEC.md` gets "Amendment A-3 (quick 261009-0qw)" once, in Task 3, covering the note placement, the phone-rule mechanism and the keyboard finding.
