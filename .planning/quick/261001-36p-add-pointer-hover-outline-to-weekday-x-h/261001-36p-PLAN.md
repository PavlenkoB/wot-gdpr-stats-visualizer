## Decisions made by the planner (record all of them in the SUMMARY)

**1. Same construction as the calendar: a state-driven SVG overlay pair, not a CSS `:hover` stroke.** HourGrid's keyboard ring is the same thing the calendar's is: a two-rect overlay drawn last in the svg, gated on a flag, with `.cell` setting `outline: none`. A stroke on a cell rect is covered on its right and bottom by the next cell (SVG has no z-index), and here the cells touch (24px cell on a 24px pitch, no gap), so a cell stroke would also fight its neighbours. The overlay construction is therefore the right fit again, driven by pointer position instead of keyboard state. Commits `1f4459d..651ec9f` are the reference (`git diff 78d038a~..651ec9f -- src`).

**2. Four places where HourGrid's structure differs from the calendar's, and what this plan does about each.**
- **The svg crops its own overflow (real difference, one added CSS declaration).** `CalendarHeatmap.svelte` sets `overflow: visible` on its svg; `HourGrid.svelte`'s `svg` rule has only `display: block`, so the browser's default `overflow: hidden` for a non-root svg applies. The ring is drawn 4px beyond the cell (inner white stroke), the bottom row and the last column sit flush against the svg's bottom and right edges (192 and 624 px), so on those cells the ring's bottom or right edge would be cut off, leaving a lopsided ring. The existing keyboard ring has the same crop today. The fix is `overflow: visible` on the svg rule; the scroller already has 4px of vertical padding and `overflow-y: hidden`, and at the 640px desktop card width there are 16px spare to the right of the 624px svg. This is a paint-only change (no layout change) and it also un-crops the keyboard ring on those edge cells; say so in the SUMMARY as the one behaviour change beyond hover. The hover ring on the corner cell (index 167) is the test for it.
- **No year blocks, no `isInYear` guard.** One svg, one fixed set of 168 indices. `hoverCell` is `model.cells[hoverIndex] ?? null`; an index can never point at a removed cell, so there is no stale-day hazard to guard beyond `undefined`.
- **The pointer-down handler is an inline arrow on the svg, not a named function.** It sets `keyboardFocus = false`. Leave it exactly as it is (a press does not move the pointer, so it must not clear the ring); the unit contract reads the inline body instead of a named function.
- **The grid's own keyboard ring rects carry `aria-hidden="true"`** (the calendar's do not). The hover pair carries it too, to match the ring in the same file; it hides a decoration from the role=grid's children. Still no `data-*`, `tabindex` or `role`.

**3. No shared helper with the calendar.** `CalendarHeatmap.svelte` is not modified. Its unit contracts count `class="focus-ring` and `class="hover-ring` in its own source (exactly twice each), so pulling the ring markup into a shared component would break those source contracts for no gain; the two components already carry parallel keyboard-ring markup.

**4. Escape dismisses the tooltip only.** The ring is pointer position, so it stays until the pointer leaves, exactly as in the calendar. Not tested.
