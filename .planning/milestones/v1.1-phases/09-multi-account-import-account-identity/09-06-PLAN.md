## Planner choices (so the executor does not "correct" them)

1. **One chain, not four copies.** The fixture matrix for one, two and three accounts is already unit-tested through the real worker (plan 09-03). The browser chain therefore runs 3, then a duplicate, then 2, then Clear, then 3 again, then 1, then Start Over, which touches every account count and both destructive controls once.
2. **No new helper in the shared helpers file.** `tests/e2e/_support/helpers.ts` is read by every spec; the raw-store reader is local to the spec that needs it.
3. **The phone check measures, and the backstop stays.** The step asserts no horizontal overflow, that each account row lies inside the viewport width, and that the full text of the long nickname and the 20-digit ID is present. Whether the wrapped result reads well is a visual judgement, kept as a backstop truth that routes to human verification, not a silent pass.
4. **Budget (D-23).** The suite lists 256 tests today (measured: `playwright test --list` prints "Total: 256 tests in 27 files"), so two new tests give 258, the ceiling. Hence the phone check is a step of the lifecycle test and the zero-network proof is a stage of an existing test. Both long tests set their own generous timeouts, as the zero-network flows do. The guard credits 5 seconds to each new listed test and prices its long specs separately (the scale constants), so two multi-minute tests counted at 5 seconds each would make the projection dishonest with 0.6 seconds of slack; Task 3 therefore measures them and follows the file's own convention. If any later change adds a listed test, all three limits must be raised together (G plus 2 minutes, W plus 8 minutes), never one.
5. **Reload is not in the zero-network stage.** A reload starts a new page load and a new worker, which the file's single-worker assertion would count as a second worker; reload is covered by the lifecycle test.
