<objective>
Close CR-01, the one gap the verification report scored as failed: a merged read bucket whose consumers resolve column keys off one account's header, so a second account with a different header has its values reported as absent while its file is plainly in the archive.

Purpose: roadmap SC2 says Phase 9 guarantees "every existing pane opens on the multi-account dataset without an error". A pane that renders the second account's real values as "not in this export" is not "without an error" — it is a false statement about the user's own data (DATA-04), and it is the one failure this phase's own verification could not clear. The precedent is already in the codebase: `readSessionRowData` and `readLoginRowData` were given account-level grouping in 09-03 for exactly this reason; the vehicles, finance and device-info readers were left merged on a premise that turned out to be false. This plan gives them the same grouping and, with it, the same per-account column resolution, and it corrects the doc comment that asserted the false premise so the defect cannot be read away again.

Output: a per-account grouped `readRowsByFile`, one seam in `data-queries.ts`, per-account column resolution in the three aggregators, a new synthetic archive whose two roots disagree on a column spelling, a tracer test that fails before the change and passes after it, and a doc comment that describes the reader as it now is.

Decisions implemented here: none new. D-11 and D-12 are preserved, not revised — every pane still reads every account's rows; only the key each row is read through changes. Phase 9's locked decisions (D-06 to D-09, D-16, D-17, D-18, D-21, D-22) are untouched, as is the Dexie `version(2)`.

Project rules honoured: no dependency added, no network request, no `Co-Authored-By` trailer (AGENTS.md), no edit to `src/lib/import`.

Note on task count and on the context budget: this plan runs three tasks and is projected at roughly 105,000 tokens against a 100,000-token smart zone, and both facts are deliberate rather than accidental.

The reason is structural, and it is the same reason for the task count. `readRowsByFile`'s return shape changes, so every builder that consumes it must change in the same commit or `pnpm run check` is red — a plan boundary is only a boundary if the tree compiles at it. Splitting the expansion (vehicles and finance) into a plan of its own would buy a budget number at the cost of leaving a red tree at the boundary, and the executor would then have to reconstruct the half-applied type change before it could do anything at all.

What the budget bought, stated plainly: the smallest correct vertical slice is the tracer (fixture, reader, seam, one consumer, one failing-first test), the expansion is the two remaining consumers, and the third task is the documentation and gate work that the verifier specifically asked for. If this plan overruns in practice, the split to make is NOT "tracer here, expansion there" — it is "the docstring and gate task last, on its own", which is safe because it changes no type.
