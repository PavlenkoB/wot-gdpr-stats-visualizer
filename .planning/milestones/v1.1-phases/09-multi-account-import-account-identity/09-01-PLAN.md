## Planner choices (so the executor does not "correct" them)

1. **D-06 and the one-root function.** `resolveCsvFileCategory(name, root: string, recognized)` has about fifteen pinned call sites and six pinned `toEqual({ category, sourceFile })` assertions, so it keeps its exact signature and behaviour. Its N-root form is the new `resolveCsvFileOwner(name, roots: ReadonlySet<string>, recognized)`, which returns `{ root, category, sourceFile }`. For a set of exactly one root it delegates to the one-root function and attaches the root, so the two cannot disagree; for two or more roots it applies a strict rule and the rightmost-root fallback is off. The inflate filter and the parse loop in plan 09-02 both call the N-root form with the same set (D-06).
2. **Where the rules live.** The multi-root resolver runs first in `analyzeExport` and returns `null` when no account root exists, so the entire v1.0 chain (rootless read, wrapper retry, named reasons) runs unchanged for every zero-root shape. `detectRoot` and `unknownFolderHoldsRecognized` are left untouched; the latter must not be reused as the multi-root rule (RESEARCH Pitfall 4).
3. **Reasons.** A stray unknown folder beside roots reports `no-single-root` (what v1.0 reported for a root beside a stray folder), a recognised top-level category beside roots or a root-name collision reports `ambiguous-root`, and the two bounds report the two new reasons. The user sees one generic banner for all of them.
4. **Bounds (RESEARCH A8, Security Domain, D-20).** `MAX_ACCOUNT_ROOTS = 32` and `MAX_ROOT_NAME_LENGTH = 128`. The name bound is needed because plan 09-02 stamps the root on every stored row (D-07); an unbounded 60 KB folder name would be copied into every row. It narrows one v1.0 shape (a single root whose folder name is longer than 128 characters now fails with the generic banner); real exports use numeric IDs. This narrowing is a recorded decision, D-20, so the plan keeps the bound for every root count including one: restricting it to several roots would let the same 60 KB name through on a single root, which is the very row-copy cost the bound exists to stop (roadmap SC4 is about the real export shapes, none of which has such a name). No code change is needed to honour D-20; the tests pin both bounds and name D-20.
5. **Open Question 6.** D-03 says an unknown wrapper holding recognised categories stays `ambiguous-root`; the pinned test for the same shape expects `no-recognized-category`. The reason is never shown, so the pinned reason is kept.
