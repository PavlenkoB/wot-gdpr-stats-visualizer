<objective>
Close the storage hole a promotion opens and prove the one folder that must stay shut. Extend the in-place narrowing step so raw rows of the promoted categories that an older build left in a returning user's cache are narrowed or deleted on the next cache check, and pin D-02 (Game_Forums stores nothing) with a regression guard.

Purpose: promoting a folder stops the D-21 purge from deleting its legacy rows, and the existing narrowing step only looks at file NAMES. Without this plan a v1.0 cache keeps Bans, Bonus_Codes, Personal_Coupons, Subscriptions, Surveys and Authorized_Third_Parties rows (IPs, codes, possibly emails) at rest forever. Separately, D-02 asks for an email test on the forum folder; the code already fails closed, so the deliverable is a guard that keeps it so.

Output: the extended `narrowStoredNewDataRows`, the legacy-seed test and the forum guard.
</objective>

src/lib/worker/db.ts narrowStoredNewDataRows(): inside one rw transaction over db.rows and db.meta it reads meta (returns 0 when none), walks `db.rows.orderBy('sourceFile').uniqueKeys()`, skips keys that are not isNewDataFile, reads `db.rows.where('sourceFile').equals(key)`, groups rows in a Map keyed by narrowGroupKey(accountOf(row, meta), key, row.category) (lower-cased file and category, NUL-separated), then per group: spec = specFor(group[0].category, key); no spec or not fileMatchesSpec(group data) -> bulkDelete the group and record stored 0; else projectRow each row and bulkPut only the rows whose projection differs (sameRowData), recording the group size. After the walk a `rewrite` closure updates meta.files and meta.accounts[].files: for a fact with isNewDataFile(file.sourceFile) whose group was visited it sets rowCount to the stored count and parsedRowCount to file.parsedRowCount ?? file.rowCount; meta is put only when something changed. Returns rows deleted plus rewritten.

db.ts also has purgeUnsupportedCategoryRows() (deletes every row whose category is not supported, walking the category index) and accountOf(row, meta) (row.account ?? meta.accountRoot). ingest.worker.ts handleCheckCache calls the purge then the narrowing, in that order.

tests/unit/import/multi-account-lifecycle.test.ts near lines 795-930 holds the pattern to copy: seedLegacyUnsupportedRows writes v1.0-shaped rows (no account field) straight into Dexie, a check-cache request goes through the real worker, and PURGE_CANARIES are asserted absent afterwards.
