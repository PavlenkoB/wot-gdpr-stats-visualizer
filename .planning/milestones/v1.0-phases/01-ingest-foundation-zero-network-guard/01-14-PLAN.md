<objective>
Close WR-03 / W-2 (01-REVIEW.md WR-03, 01-VERIFICATION.md W-2): `unzipSync` in `handleIngest` inflates every entry that resolves to a category CSV with no size check, while the enumeration step beside it is bomb-safe because its filter returns false. A small archive whose central directory declares a huge uncompressed size can force a very large allocation in the worker, which either throws mid-import or takes the renderer down.

01-RESEARCH.md (Security Domain, zip-bomb row) flagged exactly this forward: Phase 1 never inflates, "Phase 2, which does decompress supported CSVs, will need its own size-limit consideration". It never got one.

Purpose: bound the allocation by what the central directory declares, BEFORE anything is allocated, using a per-entry and a total cap, and make the zip-paths.ts documentation say what is actually true.

Limits are a deliberate choice in this plan (Claude's discretion; the review sketched 256 MiB and 1 GiB): 128 MiB per entry and 512 MiB in total. The per-entry cap is about 28 times the largest legitimate entry measured (the 60,000-session CSV), the total is about 89 times the largest legitimate export measured. Both live in one module and are reversible by editing two constants.

Output: one small pure module, one changed call site, one fixture builder, two test files, one documentation comment.

Tracer exemption: not needed. Task 1 is the tracer: one over-declared archive driven from zip bytes through the worker's filter to the error response and an empty database.

Locked decisions (01-CONTEXT.md D-01..D-17): none is reversed. Preserved: D-04 (one generic failure message), D-05 (the cause goes to console.error and the detail only), D-07 (same single error path), D-09 (message contract frozen).

<interfaces>
fflate `UnzipFileInfo` (read from node_modules/fflate/lib/index.d.ts at planning time): `{ name: string; size: number; originalSize: number; compression: number }`. `size` is the COMPRESSED size and `originalSize` is the declared uncompressed size, taken from the central directory. For a stored entry (compression 0) fflate returns a slice of the archive and never allocates from originalSize; for a deflated entry it allocates `new Uint8Array(originalSize)` before inflating.

Current code in `src/lib/worker/ingest.worker.ts` handleIngest:

```typescript
const recognized = new Set(outcome.result.categories.map((c) => c.name));
const inflated = unzipSync(bytes, {
  filter(info) {
    return resolveCsvFileCategory(info.name, outcome.result.accountRoot, recognized) !== null;
  },
});
```

An exception thrown from that filter propagates out of unzipSync into handleIngest's single try/catch, which logs it and posts `{ type: 'error', jobId, detail: '<name>: <message>' }`.

Central directory file header layout used to patch a size (PKZIP APPNOTE 4.3.12, and the offsets fflate itself reads): signature bytes 0x50 0x4B 0x01 0x02 at offset 0; compression method u16 LE at offset 10; uncompressed size u32 LE at offset 24; file-name length u16 LE at offset 28; file name starts at offset 46.

`tests/fixtures/export-fixtures.ts` already patches archive bytes for `buildInflateTrapExport` (read it for the loud-failure style). Fixtures must use the pinned `zipSync` (`tests/fixtures/pinned-zip.ts`); `tests/unit/guards/sample-export-shape.test.ts` fails a fixture that imports zipSync from fflate. A per-entry `[bytes, { level: 0 }]` value makes fflate store the entry uncompressed.
