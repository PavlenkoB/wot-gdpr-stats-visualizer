Empirical fflate 0.8.3 facts (planning-time scratch spike, 2026-09-28; RESEARCH A2 resolved):
- unzipSync(bytes, { filter }) throws `Error` with message "invalid zip data" (code 13) for: zero bytes, plain text bytes, 1 KB of non-zip bytes, a zip truncated to 60% of its length, and a zip missing only its last 10 bytes.
- unzipSync on zipSync({}) (a valid, empty zip) returns without throwing, so the filter sees 0 entries.
- For an archive whose first local entry (method 8, deflate) has 8 data bytes overwritten with 0xFF, filter-only enumeration lists every entry, while a full unzipSync with no filter throws "invalid block type".
- Entry names come back raw. Backslash separators and `__MACOSX/...` / `.DS_Store` entries are returned verbatim. zipSync keys ending in "/" with an empty Uint8Array produce directory entries.
- Local file header layout: compression method is a little-endian u16 at offset 8, file-name length a u16 at offset 26, extra-field length a u16 at offset 28, and data starts at 30 + nameLen + extraLen. zipSync writes entries in object-key insertion order, so the first key sits at offset 0.

|----------|-------------|
| user file → worker | Zip bytes and entry names are attacker-controllable input parsed inside the worker. |
| worker → main thread | Classification results (entry-derived strings) and error details cross via postMessage and are later rendered or logged. |
